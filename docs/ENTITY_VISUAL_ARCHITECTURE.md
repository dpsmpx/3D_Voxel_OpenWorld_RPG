# Визуальная архитектура сущностей

Разбор всего пути от игровой сущности до пикселя на экране, с одним
вопросом: почему животное стоит правильно, а идёт боком.

Этап 1 — аудит. Код не изменён: это опись с доказательствами.
Правила, по которым всё будет перестроено, — раздел 6.

---

## 1. Цепочка целиком

```
mobs::MobAI / npc::NpcAI     ← состояние, скорость, фаза шага
        │
ecs::Transform.position       ← где сущность
ecs::Velocity.linear          ← куда движется
        │
MobRenderer::rebuild()        ← yaw считается ЗДЕСЬ, каждый кадр заново
        │  yaw = atan2(vel.x, vel.z)
        │  offset частей поворачивается на процессоре
        ▼
MobInstance { pos, size, color, yaw }
        │
shaders/mob.vert              ← куб поворачивается ЗДЕСЬ, второй раз
        ▼
                              GPU
```

Состояние поворота не хранится **нигде**. Ни в `ecs`, ни в `MobAI`,
ни в `NpcAI`: `yaw` — локальная переменная внутри `rebuild()`, живущая
один кадр.

| стадия | где лежит | кто пишет | кто читает |
|---|---|---|---|
| положение | `ecs::Transform` | физика, ИИ | рендер |
| скорость | `ecs::Velocity` | ИИ | рендер |
| **поворот** | **нигде** | — | — |
| фаза шага | `MobAI::walkPhase` | ИИ | рендер |
| поза | вычисляется в рендере | — | — |

## 2. Причина бокового хода

### 2.1 Процессор и шейдер поворачивают в РАЗНЫЕ стороны

Соглашение задано строкой `yaw = atan2(vel.x, vel.z)`: ноль смотрит в
`+Z`, угол растёт к `+X`. Значит локальное `+Z` обязано отображаться в
`(sin yaw, cos yaw)`.

**Шейдер** (`mob.vert:44`) делает именно это:

```glsl
vec3 rotated = vec3(local.x*c + local.z*s, local.y, -local.x*s + local.z*c);
```

**Процессор** (`mob_renderer.cpp:210`, `npc_renderer.cpp:185`) делает
обратное:

```cpp
inst.pos.x += off.x * c - off.z * s;
inst.pos.z += off.x * s + off.z * c;
```

Это поворот противоположной ручности. Подстановка:

| направление | yaw | ожидание для `+Z` | шейдер | процессор |
|---|---|---|---|---|
| +Z (север) | 0° | (+0.00, +1.00) | (+0.00, +1.00) | (+0.00, +1.00) |
| **+X (восток)** | 90° | (+1.00, +0.00) | (+1.00, +0.00) | **(−1.00, +0.00)** |
| −Z (юг) | 180° | (+0.00, −1.00) | (+0.00, −1.00) | (−0.00, −1.00) |
| **−X (запад)** | −90° | (−1.00, +0.00) | (−1.00, +0.00) | **(+1.00, +0.00)** |
| **диагональ** | 45° | (+0.71, +0.71) | (+0.71, +0.71) | **(−0.71, +0.71)** |

Совпадение только при движении **вдоль Z**. При любом движении с
составляющей по X **положения частей зеркалятся по X, а геометрия
частей — нет**: тело собирается наизнанку. Голова оказывается там,
где хвост, ноги переставлены местами — и существо выглядит идущим
боком.

### 2.2 Почему в покое всё выглядит правильно

```cpp
f32 yaw = 0.f;
if (glm::length(velXZ) > 0.1f) {
    yaw = std::atan2(velXZ.x, velXZ.y);
}
```

`yaw` **обнуляется каждый кадр**. Как только скорость падает ниже
0.1, поворот мгновенно становится нулевым — то есть «на север», где
процессор и шейдер согласны. Отсюда и наблюдение: стоит правильно,
идёт боком.

Это же — второй дефект: **поворот скачком**. При старте сущность
мгновенно доворачивается в сторону движения, при остановке мгновенно
разворачивается на север. Плавного доворота нет и быть не может:
хранить промежуточное состояние негде.

### 2.3 Чего в коде НЕТ

Поиск по `render/`, `mobs/`, `npc/` не нашёл ни одной точечной
коррекции поворота: ни `+90°` для отдельного вида, ни `if (species ==
X) invert Z`, ни отдельного случая в рендере. **Ошибка ровно одна и
она системная** — это хорошая новость: чинится в одном месте, а не в
десяти.

## 3. Оснастка и анимация

### 3.1 Иерархии нет

`MobPart` — плоская запись:

```cpp
struct MobPart {
    glm::vec3 offset;    // от начала сущности, без родителя
    glm::vec3 size;
    u32       color;
    PartAnim  anim;
};
```

Ни родителя, ни локальной системы координат части. Девять
фиксированных слотов (`Part_Body`, `Part_Head`, `Part_LegFR`…). Собрать
`торс → бедро → голень` невозможно: всё висит на корне.

### 3.2 Анимация двигает части, а не вращает

```cpp
case mobs::PartAnim::Leg:
    off.z += std::sin(phase) * 0.15f * speedNorm * mult;
```

Нога **сдвигается** вперёд-назад, оставаясь параллельной себе. Живое
существо вращает конечность в суставе. Отсюда «плывущая» походка:
ступня не описывает дугу, а скользит по прямой.

### 3.3 Фаза шага гонится временем, а не путём

```
mob_ai.cpp:292   ai->walkPhase += dt * 1.f;    // Idle
mob_ai.cpp:298   ai->walkPhase += dt * 2.f;    // Wander
mob_ai.cpp:334   ai->walkPhase += dt * 6.f;    // Chase
mob_ai.cpp:382   ai->walkPhase += dt * 9.f;
```

Частота шага — константа на состояние ИИ, не зависящая от фактической
скорости. Значит длина шага и пройденный путь не связаны: это и есть
скольжение ног. Вдобавок фаза продолжает расти в `Idle`.

### 3.4 Конечного автомата состояний нет

Нет ни `Idle/Walk/Run/Turn/Jump/Fall/Land`, ни переходов, ни
смешивания. Есть одно число `speedNorm`, умножающее амплитуду синуса.
Требуемых заданием переходов реализовать не на чем.

## 5. Деревня

`features.cpp:425`, `stampHouse`:

* стены — полый ящик из `WOOD`, 4 блока высотой, с проёмом двери;
* «крыша» — два плоских слоя `LEAVES` со ступенькой наружу и сверху
  ещё одна плоская плита листвы. Формы крыши нет: это гриб;
* «факел» — блок **`LAVA`** в середине комнаты;
* фундамент — плита `STONE`.

`stampVillage` расставляет 6–10 таких ящиков **по окружности** радиуса
20–36 через равный угол, все выровнены по осям мира, отличаются только
размером 5–8. Ни дорожек, ни изгородей, ни утвари, ни площади, ни
ориентации домов к центру.

То есть деревня буквально «генератор поставил несколько коробок». Это
ровно то, что видно на экране.

## 6. Правила, по которым это будет перестроено

Раздел — источник истины для всех будущих сущностей.

### 6.1 Система координат

* Мир правосторонний, **`+Y` вверх**.
* **Модельное `+Z` — «вперёд»**, `+X` — «вправо», `+Y` — «вверх».
* Поворот сущности — один угол `yaw` вокруг `+Y`.
* `yaw = 0` смотрит в `+Z`; угол растёт **к `+X`**.
* Направление по yaw: `forward(yaw) = (sin yaw, 0, cos yaw)`.

Из этого следует **единственная** допустимая матрица поворота, и она
обязана быть одна и та же на процессоре и в шейдере:

```
x' =  x·cos(yaw) + z·sin(yaw)
z' = -x·sin(yaw) + z·cos(yaw)
```

Сейчас процессор использует другую. Это и есть правка этапа 2.

Начиная с этапа 3 поворот в инстансе — **кватернион**, а не угол:
одним углом повёрнутую в суставе конечность выразить нельзя. Формула
остаётся той же: `qrot(yawQuat(a), v)` обязан дословно совпадать с
`rotateY(v, a)`, и за этим следит численная проверка. Кватернионы
строятся в `core/orientation.h` — там же, где и матрица, чтобы
«вперёд» значило одно и то же в обоих представлениях.

### 6.2 Поворот — состояние, а не вычисление

У сущности заводится хранимый `facing` (yaw) и отдельно
`movementDirection`. Правила:

* `movementDirection` берётся из скорости, но **только когда она
  значима**; иначе сохраняется прежняя;
* `facing` **догоняет** `movementDirection` с ограниченной угловой
  скоростью, по кратчайшей дуге;
* при остановке `facing` **не меняется**: существо остаётся смотреть
  туда, куда шло;
* рендер читает `facing` и **не вычисляет** его сам.

### 6.3 Если модели нужна своя ориентация

Только явным полем в определении модели (`modelYawOffset`), рядом с
геометрией. Никаких поправок в рендере, ИИ или по имени вида.

### 6.4 Оснастка

Части получают **родителя** и собственную локальную систему:
`корень → торс → (голова, бёдра, плечи) → (голени, предплечья) →
(ступни, кисти)`. Преобразование части — поворот вокруг её сустава,
затем смещение к родителю. Анимация вращает суставы, а не сдвигает
коробки.

**Оснастка не меняет размер модели.** Оснастка — то же существо,
пересобранное с суставами, а не другое: если звенья ноги в сумме
длиннее исходной коробки, существо молча вырастает. Проверка сверяет
рост оснастки с ростом плоского определения.

**Подошва садится на опору.** Начало сущности совпадает с точкой
опоры: контроллер ставит `position.y` ровно на пол. Поэтому низ модели
в покое обязан быть у нуля, и сборщик оснастки выводит `groundOffset`
из геометрии — **одним правилом для всех видов**, а не поправкой на
вид. Плоские определения это правило выдерживали не везде: Каменный
страж стоял по щиколотку в полу. Летающие и плавающие переопределяют
`groundOffset` явно, после сборки; это единственное законное место для
такой поправки.

**Сгиб конечности — анатомия, а не вкус.** Поворот сустава на
положительный угол по X уводит нижнее звено назад, в `-Z`. Отсюда:
передние ноги и руки складываются назад, задние ноги — вперёд
(коленный сустав зверя смотрит вперёд, скакательный назад). Проверять
это надо **положением голени**, а не знаком угла: проверка, сверяющая
знак с той же функцией, которая его задаёт, принимает любой знак.

### 6.4a Двуногий — одна оснастка на всех

Селянин, страж, кузнец и игрок — один `humanoidRig`, отличающийся
пропорциями и цветами из определения вида. Пропорции задаются
**долями роста**, а не числами в метрах: тогда один набор одинаково
ложится и на приземистого кузнеца, и на рослого стража. Отдельного
кода на каждого быть не должно — именно так и появляются шесть коробок,
собранных руками прямо в рендере.

### 6.4b Вершинный формат объявляется один раз

Четыре рендера (мобы, NPC, предметы, снаряды) делят формат инстанса
`MobInstance`. Его таблица `VertexAttr`, таблицы куба и смещения полей
объявляются **в одном месте** — `render/mob_renderer.h`. Дословные
копии в каждом рендере и были исходной ошибкой: при смене формата
правку получал один файл из четырёх, а остальные продолжали читать
чужие байты. Vulkan об этом не сообщает, картинка просто становится
мусором. Смещения в таблице сверяются с полями структуры
`static_assert`-ами, а отсутствие копий — проверкой `check_winding.py`.

### 6.5 Фаза шага — от пути, а не от времени

```
walkPhase += distanceTravelled / strideLength · 2π
```

Тогда длина шага согласована со скоростью по построению, и скольжения
ног не бывает: это не настройка, а следствие формулы.

### 6.6 Состояния

`Idle → Walk → Run` и обратно, плюс `Jump/Fall/Land`, с переходом по
времени и смешиванием поз. Переключение — по фактической скорости и
признаку опоры, а не по состоянию ИИ.

## 7. Чего этот аудит не трогает

Камера, боевая логика, ИИ, физика, формат сохранения. Всё найденное
лежит в `render/`, `mobs/`, `npc/`, `shaders/mob.vert` и
`world/features.cpp`.

Опора по производительности: кадр 9.9 мс на устройстве, сущности
рисуются одним инстансным вызовом на куб. Новые модели не должны это
ломать — считать цену в вершинах до, а не после.
