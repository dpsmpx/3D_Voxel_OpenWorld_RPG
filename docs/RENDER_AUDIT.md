# Разбор пути отрисовки: от вокселя до кадра на экране

Карта построена по ИСХОДНОМУ КОДУ и по КАРТИНКЕ С УСТРОЙСТВА.
Комментарии, прежние проверки и прежние выводы источником истины
не считаются: там, где комментарий расходится с кодом, записан код;
там, где код расходится с картинкой, записана картинка.

Состояние на коммит `fb87bda`, ветка `claude/project-full-review-4757sr`.
Устройство: 2306×1080, экран повёрнут на 90°, `depth=126`
(`VK_FORMAT_D32_SFLOAT`), слоя проверки на устройстве нет.

Обозначения в графах: **СК** — система координат, **Y** — куда растёт
Y, **обход** — порядок вершин лицевой грани, **влад.** — кто владеет
памятью и сколько она живёт.

## 1. Воксельные данные

| | |

| вход | генератор рельефа / загрузка сейва / правки игрока |
| выход | `world::Chunk::voxels` — `std::array<u16, 131072>` |

| индекс | `(y * 32 + z) * 32 + x`, `chunk.h:24` |
| СК | локальная для чанка: `x,z ∈ [0,32)`, `y ∈ [0,128)` |
| единицы | 1 воксель = 1 блок = 1 мировая единица |
| правша | да; мир: X вправо, **Y вверх**, Z на зрителя |
| Y | вверх |
| влад. | `std::shared_ptr<Chunk>`, поле нуль-инициализировано (`voxels{}`) |

грязной памяти в этом звене нет.

## 2. Жадное меширование — `world::buildGreedyMeshInto`, `chunk.cpp:322`

| | |
|---|---|
| вход | `Chunk` + `ChunkNeighbors` (4 соседа по X/Z, **любой может быть `nullptr`**) |
| выход | `std::vector<world::Quad>` / `std::pmr::vector<Quad>` |
| СК | КЛЕТКИ выбранного уровня, перевод в блоки один раз при записи квада |
| единицы | клетка = `step = 1 << lod` вокселей: 1, 2, 4, 8 |
| обход | здесь ещё нет — квад хранится как `origin + du + dv` |
| нормаль | `q.v0.face`, индекс 0..5 в порядке `+X, −X, +Y, −Y, +Z, −Z` |
| влад. | арена воркера (`mem::Arena`, thread_local), затем копия в `chunk.meshes[lod].quads` |
| синхр. | `shared_lock` на свой чанк и на всех ненулевых соседей, захват в порядке возрастания адреса; результат под `chunk.meshMutex` |

Оси граней (`FACES`, `chunk.cpp:52`):

| грань | u | v | w | знак |
|---|---|---|---|---|
| +X, −X | Y | Z | X | +1 / −1 |
| +Y, −Y | X | Z | Y | +1 / −1 |
| +Z, −Z | X | Y | Z | +1 / −1 |

Начало квада: `org[w] = (slice + (sign > 0 ? 1 : 0)) * step`,
`org[u] = iu * step`, `org[v] = iv * step`;
`du[u] = wU * step`, `dv[v] = wV * step`.

Затенение и небо считаются в клетке **перед** гранью (`n = c + sign`
по оси w) — то есть в воздухе, а не в теле блока. Для верхней грани
это даёт открытость 7. Журнал устройства это подтверждает: у верхних
граней доля открытых 0.95..1.00.

Слияние требует совпадения блока, AO и неба разом — иначе тень свода
растеклась бы по освещённому склону.

## 5. Загрузка через staging — `ChunkRenderer::uploadLod`, `chunk_renderer.cpp:78`

| | |
|---|---|
| вход | `scratchVerts_` / `scratchIndices_` |
| выход | копия в device-local буфер |
| индекс | `u16`, если вершин ≤ 65535, иначе `u32`; тип пишется в `gm.indexType` |
| влад. | `vk::StagingPool` — буфер занят `TRANSFER_SLOTS` пакетов после `retire()` |
| синхр. | барьер `VERTEX_INPUT → TRANSFER` в начале пакета и `TRANSFER → VERTEX_INPUT` в конце; `beginTransferBatch` ждёт забор слота перед переиспользованием командного буфера |

Время жизни staging сходится: буфер, отданный в пакете N, помечается
свободным при `collect()` кадра N+K, а `beginTransferBatch` того же
кадра ждёт забор пакета N до того, как `acquire()` его выдаст.

## 10. Фрагментный шейдер террейна — `voxel.frag`

| | |
|---|---|
| точность | `precision mediump float; precision mediump int;` — на мобильном GPU это fp16 |
| highp явно | `vWorldPos`, `cell`, `fp`, `f`, `d`, `hash13`, `toFrag`, `V` |
| **mediump по умолчанию** | **весь блок `CameraUbo`, включая `cameraPos` и `viewProj`**, а также `vColor`, `vShade` |
| нормаль | `FACE_N[face]`, `face` из `flat uint` — плоская, per-primitive |
| освещённость грани | `FACE_LIGHT[6]` = верх 1.00, ±Z 0.88, ±X 0.76, низ 0.50 |
| фаска | `fract` от мировых координат, только ЗАТЕМНЯЕТ, диапазон `[0.82, 1.0]` |
| свет | ровный рассеянный (цвет неба, приглушённый к белому) × AO × открытость неба + одно направленное солнце |
| туман | по расстоянию, `smoothstep`, цвет неба с подмесом солнца |

Зерна (крапчатости по номеру вокселя) здесь больше нет, как и двух
подкрасок — волны по мировым координатам и градиента по высоте. См.
раздел «Воксельный вид» в конце файла.

Проверено численно: `ambient` для верхней грани при открытом небе
даёт множитель ≈0.63..0.86, ни одно слагаемое не может дать резкий
светлый прямоугольник в четверть блока (см. п. 21).

## 13. Отсечение граней

Геометрия всюду намотана против часовой стрелки при взгляде снаружи:

## Найденные противоречия

### П1. Порядок каналов цвета у всех инстансных кубов — ПОДТВЕРЖДЁН

Процессор складывает цвет как `0xRRGGBBAA`:

```cpp
// mob_def.cpp:11
constexpr u32 rgb(u8 r, u8 g, u8 b) {
    return ((u32)r << 24) | ((u32)g << 16) | ((u32)b << 8) | 0xFF;
}
// item_renderer.cpp:58
case items::ItemRarity::Uncommon: return 0x60D060FF;
```

Видеокарта читает те же четыре байта **в порядке памяти**:

```cpp
{ 3, 1, VK_FORMAT_R8G8B8A8_UNORM, 24 },   // iColor
```

На порядке байтов от младшего (ARM, x86) `u32 0xRRGGBBAA` лежит в
памяти как `AA BB GG RR`. Значит шейдер получает
**R = A, G = B, B = G, A = R**. Никакого обратного перестроения нет:
`mob.vert` делает `vColor = iColor;`, `mob.frag` — `toLinear(vColor.rgb)`
и `outColor.a = vColor.a`.

Последствия:

* тело коровы `rgb(80,60,40)` — тёмно-коричневое — приходит в шейдер
  как **(255, 40, 60)**, ярко-красное. На снимке с устройства на
  тёмном склоне действительно видны ярко-красные и малиновые
  прямоугольники там, где стоят мобы;
* у всех цветов редкости предметов `AA = FF`, значит **R = 1.0** у
  каждого выпавшего предмета;
* альфа берётся из байта R. Для непрозрачных проходов это почти
  безобидно, но конвейер снарядов объявлен со смешиванием — там
  прозрачность получается произвольной.

Затронуты: `mob_renderer`, `npc_renderer`, `item_renderer`,
`projectile_renderer`. **Не затронуты** террейн (`emitQuad`
распаковывает байты вручную) и трава (`GrassInstance` хранит
отдельные `u8 r, g, b, a`).

То есть в проекте сосуществуют два несовместимых соглашения о цвете, и
ни одна проверка их не сличала.

### П6. Точность межстадийных переменных не совпадает — ПОДТВЕРЖДЕНО В SPIR-V

`voxel.vert` не объявляет точности вовсе, то есть по умолчанию весь он
`highp`: в скомпилированном модуле **ноль** декораций
`RelaxedPrecision`. `voxel.frag` начинается с
`precision mediump float; precision mediump int;` — в нём таких
декораций **340**. Разошлись ровно межстадийные переменные:

| переменная | вершинный | фрагментный |
|---|---|---|
| `vColor` (0) | нет (highp) | **RelaxedPrecision** |
| `vWorldPos` (1) | нет | нет — совпадает |
| `vShade` (2) | нет (highp) | **RelaxedPrecision** |
| `vInfo` (3) | нет (highp) | **RelaxedPrecision** |

Три переменные из четырёх объявлены в двух стадиях с разной точностью.
Правила стыковки интерфейсов в Vulkan сверяют тип и расположение, а
декорацию точности — нет, так что модуль проходит проверку; но хранит
и передаёт такую переменную драйвер по своему усмотрению.

Важно, ЧТО именно разошлось: `vShade` — это запечённые затенение углов
и открытость неба, и множители освещения из них не ограничены сверху:

```glsl
float ao  = 0.42 + 0.58 * vShade.x;
float sky = 0.18 + 0.82 * vShade.y;
```

Пока `vShade` лежит в [0,1], множитель не выходит за единицу. Стоит
значению уехать — освещение уезжает вместе с ним в обе стороны, без
всякого предела.

Именно это и видно на устройстве. Снимок 2400×1080, обычный мир, зерно
12648430, камера 4.5 34.0 −0.7:

* **46 %** кадра имеет хотя бы один канал, упёртый в 255 (зелёный в
  34 %, красный в 12 %);
* **18 %** кадра — чистый чёрный;
* небо при этом правильное: (125,168,236) — его рисует другой шейдер.

Тот же шейдер, то же зерно и та же камера на хосте дают землю
**(112,177,74)** — ровно то, что предсказывает формула. На устройстве в
этом прогоне **(178,255,125)**, в прогоне до этого — **(54,80,32)**.
Формула не может дать ни того, ни другого: `shoulder` упирает
максимальный канал в 1.25, а для насыщения зелёного нужен множитель
света около 2.4 при потолке формулы 0.9.

ЧЕГО ЭТО НЕ ДОКАЗЫВАЕТ. Половинная точность сама по себе уже
проверена и отброшена: кадр, нарисованный после
`spirv-opt --convert-relaxed-to-half`, отличается от обычного не более
чем на 3 из 255. То есть дело не в том, что 16 бит мало для чисел
0..1, — а в том, что переменная объявлена по-разному в двух стадиях.
Проверить это можно только на устройстве: программная реализация
Vulkan декорацию игнорирует и считает всё в 32 битах, поэтому хост
расхождение не воспроизводит по построению.

### П2. Вьюпорт и ножницы задаются не всеми проходами

Трава и контур блока полагаются на динамическое состояние, выставленное
предыдущим проходом. Динамическое состояние не наследуется между
командными буферами, и порядок проходов — единственное, что сейчас
удерживает это от неопределённого поведения. Слоя проверки на
устройстве нет, поэтому предупреждения об этом никто не увидит.

### П3. Вода рисуется до мобов, предметов, снарядов и травы

Вода читает глубину, но не пишет её. Всё, что нарисовано после неё и
находится ЗА ней, пройдёт тест глубины по дальнему непрозрачному
фону и ляжет поверх воды.

### П4. Комментарий о повороте расходится с кодом

`camera.h` говорит «мы пообещали композитору поворот через
preTransform, значит поворачиваем содержимое сами», а
`vk_context.cpp` просит `IDENTITY` и оставляет поворот композитору.
Ветка доворота в проекции на этом устройстве мертва. Расхождение
документации, не поведения, но именно оно уже стоило одного круга.

### П5. Соседи при меширования могут быть `nullptr`

`gatherNeighbors` возвращает то, что загружено; `sampleVoxel`
подставляет `AIR` за отсутствующего соседа. Пересборки меша при
появлении соседа не происходит, если не менялась `version` чанка.
Затрагивает только одно кольцо блоков на стыке чанков, то есть
объяснить решётку с шагом в один блок не может, но остаётся
несоответствием между «данные полные» и «данные какие есть».

**Закрыто.** `sampleVoxel` отдаёт `UNKNOWN`, мешер по такой границе
грань не строит, а появление соседа ставит стык на перемешивание.

### П7. Уровень детализации выбирали двое, и по разным меркам

Мир (`ChunkManager::jobGenerate`) мерил расстояние от чанка ИГРОКА до
чанка в квадратах чанков; рендер (`ChunkRenderer::render`) — от КАМЕРЫ
до центра чанка в блоках. Величины разные, границы уровней у каждого
свои, мёртвая зона была только у рендера. У границы стороны спорили
каждый кадр: мир строил один уровень, рендер тут же заказывал другой.

К этому прилагались три отдельных механизма, каждый со своим
последствием:

* задача меширования выбрасывала ВСЕ прочие уровни чанка, как только
  бралась строить новый, — включая тот, который сейчас на экране;
* рендер, не найдя нужного уровня, брал первый попавшийся из четырёх, а
  набор «попавшихся» менялся сам по себе;
* самый грубый уровень (шаг 8) начинался на 0.90 дальности, а туман
  кончался на 0.94 — девять процентов дальности самой грубой геометрии
  были видны у горизонта.

**Закрыто.** Формула одна на весь проект (`world/lod.h`), считается от
позиции камеры, с мёртвой зоной у обеих сторон; резидентный уровень
живёт до успешной загрузки нового и служит единственным запасным
вариантом; грубейший уровень уведён за конец тумана.

### П8. Прозрачное сортировалось по центру чанка

Проход со смешиванием шёл в обратном порядке непрозрачного, то есть по
расстоянию до ЦЕНТРА чанка — а тот лежит на половине высоты мира, в
шестидесяти с лишним блоках над водой. Порядок выходил почти
случайный. Сюда же — огрубление воды: клетка 8³ доставалась верхнему
вокселю, и берег шириной в полклетки становился прозрачным, а озеро
под одиноким выступом исчезало целиком.

**Закрыто.** Меш хранит центр своей прозрачной геометрии, взвешенный
по площади граней; проход со смешиванием сортируется отдельным
списком по нему. Огрубление решает по колонкам: клетка становится
водой, только если вода наверху у большинства колонок.

### П9. pow() с нулевым основанием — ПОДТВЕРЖДЁН НА УСТРОЙСТВЕ

Вся геометрия дальше начала тумана рисовалась угольно-чёрной. Граница
чёрного совпадала с границей тумана попиксельно: кадры устройства и
хоста, совмещённые по приметам сцены, расходятся на два пикселя, и
ровно там, где на хосте туман перестаёт быть нулевым, на устройстве
начинается чёрное. Ближе — картинка верная, дальше — чёрное до самого
края мира. В нескольких пикселях внутри чёрного, наоборот, светлее
неба.

`pow(x, k)` везде считается как `exp2(k * log2(x))`, и при `x = 0` это
`log2(0) = -inf`. Что выйдет дальше — дело драйвера. Основание здесь
обнуляется постоянно:

    float sunAmt   = max(dot(normalize(toFrag), cam.sunDir.xyz), 0.0);
    vec3  fogColor = mix(skyLin, sunTint, pow(sunAmt, 8.0) * 0.30 * above);

`max(dot(...), 0.0)` равен нулю для любого фрагмента, отвёрнутого от
солнца, — то есть для половины кадра. Результат уходил в цвет тумана, а
`toSrgb` со своим `max(c, 0.0)` превращал его в ноль.

Три независимых свидетельства:

* `voxel.frag` — ЕДИНСТВЕННЫЙ шейдер проекта, объявленный
  `precision mediump float`, и единственный, где виден артефакт.
  `grass.frag` и `mob.frag` считают ровно ту же формулу тумана с тем же
  `pow(sunAmt, k)`, но в полной точности — и трава с мобами на том же
  кадре нарисованы верно.
* Второй `pow` в `voxel.frag` стоит в ветке для полупрозрачного — блик
  и Френель на воде. На кадре устройства чёрным залито и пятно воды.
* Программный Vulkan (lavapipe, fp32) на той же сцене даёт правильный
  туман: `pow(0, k)` там ноль, и артефакт не воспроизводится по
  построению.

**Закрыто.** В `voxel.frag` не осталось ни одного `pow`: показатели 8,
64 и 4 — степени двойки, они раскладываются умножениями (точнее и
дешевле). Весь расчёт тумана объявлен `highp`, вес подмешивания и
итоговый цвет ограничены своими диапазонами. В остальных шейдерах
основание подпирается снизу через `powSafe`. Заодно исправлен
`smoothstep(0.0, -0.25, up)` в `sky.frag`: `edge0 >= edge1` по
спецификации не определено.

### П10. Огрубление поднимало и выдумывало воду — ПОДТВЕРЖДЁН

После П9 на дальнем плане остались бледные голубые плиты, стоящие над
берегом и просвечивающие небом. Программный Vulkan воспроизводит их на
том же зерне мира, что и устройство, и рядом с кадром полной
детализации видно, во что превращается ледяная гладь: плоский лист на
воде — в отдельные кубы, висящие выше снега.

Причина не в прозрачности, а в геометрии. Огрублённая клетка рисуется
ЦЕЛЫМ кубом со стороной step, поэтому высота поверхности округляется
вверх — на step-1 блоков. Для непрозрачного это незаметно: силуэт
дальнего склона чуть полнее настоящего, и только. Для воды и льда —
это плита, поднятая над берегом.

Замеры по настоящему рельефу (7x7 чанков, зерно игры) показали два
отдельных механизма:

* **Подъём.** Вся вода этого мира стоит так, что её верхний воксель
  попадает в САМЫЙ НИЗ клетки восьмого шага (верх глади на
  `y ≡ 1 (mod 8)`). Значит верх клетки — на семь блоков выше глади.
* **Выдумывание.** Правило «в клетке есть хоть один непустой воксель»
  отдавало весь куб паре колонок: кромка озера у обрыва, где занято
  16 колонок из 64, становилась целой плитой воды. На восьмом шаге
  такие колонки составляли 4 % всей водной поверхности: вода вставала
  на месте суши.

**Закрыто.** Три правила. Прозрачное берёт клетку, только если занимает
её: большинство непустых колонок И три четверти всех. Гладь не
поднимается: если вода не доходит до верхнего слоя клетки, а слой под
клеткой водой занят, клетка отдаётся пустоте — нижняя удержит
поверхность на блок ниже настоящей вместо семи выше. И начиная со
второго уровня (дальше ста сорока блоков, где туман съедает пятую часть
цвета) вода с льдом рисуются непрозрачными: смешивать там нечего, а
любая неточность сетки уровня на прозрачном читается как стекло.

Отличие кадра с огрублением от кадра полной детализации: было 19017
заметно отличных пикселей, стало 14039.

### П11. Щели на стыке уровней детализации — ПОДТВЕРЖДЁН ЗАМЕРОМ

Рельеф вдали то рисуется, то сквозь него видно небо, причём кадр к
кадру, на неподвижной камере.

Чанк строит свои граничные грани, огрубляя соседа СВОИМ шагом: клетка
соседа считается занятой, если в ней есть хоть один воксель, и стена
строится только выше этой клетки. Сосед же, огрублённый своим — более
мелким — шагом, ставит поверхность НИЖЕ, внутри той же клетки. Между
ними остаётся щель во всю длину стыка.

Замер по настоящему рельефу, 42 стыка соседних чанков:

| уровни | колонок со щелью | площадь щели | не закрыто | макс |
|---|---|---|---|---|
| 3 и 0  | 1068 из 1344 | 5154 | 4722 (92 %) | 13 |
| 3 и 1  |  956 из 1344 | 4424 | 4008 (91 %) | 12 |
| 2 и 0  |  876 из 1344 | 2133 | 1861 (87 %) |  9 |
| 1 и 0  |  568 из 1344 |  733 |  585 (80 %) |  7 |
| 3 и 3  |   32 из 1344 |  256 |    0 (0 %)  |  0 |
| 2 и 2  |   68 из 1344 |  272 |    0 (0 %)  |  0 |

При СОВПАДАЮЩИХ уровнях щелей нет вовсе — мешер верен. Открыто только
на стыке разных. Меняется уровень — меняется рисунок щелей, и это то
самое мигание.

**Закрыто.** Юбка: на крайнем слое чанка грань строится не только
когда клетка соседа пуста, но и когда она занята НЕ ЦЕЛИКОМ. Заполнена
целиком — щели взяться неоткуда ни при каком уровне соседа; не
заполнена — сосед помельче поставит поверхность где-то внутри неё, и
всё ниже окажется дырой. При совпадающих уровнях юбка оказывается
внутри соседа и невидима.

Сквозные дыры в кадре (пиксели, где при огрублении видно небо, а при
полной детализации — рельеф), четыре ракурса с одной точки:
1698 → 823, 1477 → 1, 456 → 0, 1390 → 602. Остаток на двух ракурсах —
не дыры, а дальняя вода: она с этого уровня непрозрачная и по цвету
близка к небу, детектор их не различает.

Цена: меширование грубейшего уровня 908 → 962 мкс на чанк (+6 %), на
остальных уровнях в пределах разброса.

## Что противоречиями НЕ объясняется

Главный видимый артефакт — решётки светло-зелёных прямоугольников
поверх уже отрисованного ландшафта. Измерено по снимку 2400×1080:

* размер метки 4..8 пикселей по обеим осям, **не зависит от глубины**:
  медиана высоты 3 пикселя и у горизонта, и под ногами;
* шаг решётки совпадает с шагом сетки блоков в том же месте кадра
  (автокорреляция чистой земли на `y = 880` даёт период 32 пикселя,
  метки там же стоят через 32 пикселя) — **одна метка на блок**;
* метка — прямоугольник с резкой границей примерно в четверть блока,
  в одном и том же месте каждого блока;
* **цвет метки постоянен и не зависит от подложки**: по 583 меткам
  фон меняется от (45,63,26) до (55,83,37), метка везде (100,213,137).
  Значит это отдельный материал, а не подсветка поверхности;
* меток порядка 550, тогда как трава в том же кадре — 104 пучка;
* над чистым небом меток нет (2 пикселя на 68 тысяч) — значит
  геометрия с тестом глубины, а не наложение поверх кадра.

Проверено и отброшено: трава (радиус 40 блоков, пучок на предельной
дистанции занимает 21 пиксель — метки в 4 пикселя не бывает; и метки
не изменились, когда лист сузили втрое), затенение (журнал показывает
открытость неба 0.95..1.00), половинная точность (кадр, нарисованный
настоящим fp16 после `spirv-opt --convert-relaxed-to-half`, отличается
от обычного не более чем на 3 из 255), дальние уровни детализации
(радиус проверки поднят до дальности прорисовки, 225 чанков,
уровни 16/40/64/105 — меток нет), разрешение и пересжатие снимка.

Ни одно слагаемое `voxel.frag` не способно дать резкий светлый
прямоугольник в четверть блока: зерно постоянно на целый блок и
ограничено ±15 %, фаска только затемняет и ограничена 0.84,
подкраска и высота меняются плавно.

**Вывод: артефакт не воспроизводится ничем, что доступно на хосте, и
не объясняется ни одним слагаемым шейдера террейна. Следующий шаг —
минимальная детерминированная сцена, одинаковая на хосте и на
устройстве, и сравнение кадров.**

## Минимальная детерминированная сцена

Строит её одна функция — `world::buildMinimalScene`
(`app/src/main/cpp/src/world/debug_scene.cpp`), — а рисуют оба
рендера. Сцена не зависит ни от зерна мира, ни от шума, ни от порядка
загрузки соседей; повторная сборка даёт тот же чанк до последнего
вокселя (проверяется в hostcheck).

Содержимое (нулевой чанк, приметы в блоках):

| примета | где |
|---|---|
| ровная земля | камень до y=28, земля 28..30, трава на y=31; верх — y=32 |
| один поднятый блок | камень в (8, 32, 20) |
| одна лесенка | x 12..19, z 4..11, высота растёт на блок за шаг |
| одна вода | x 22..29, z 16..23; дно камень на y=29, вода 30..31, верх вровень с землёй |
| одно дерево | ствол (5, 32..35, 6), крона 5×5×3 со срезанными углами |
| трава | по тому же хешу, что в игре, от высоты `SCENE_GROUND_Y` |
| небо | обычный проход неба |
| игрок | камера в (16.5, 44.0, −18.0), yaw 0, pitch −0.50 |

Соседние чанки — та же ровная земля: они дают центральному честных
соседей, и на стыках нет швов.

Прибито всё, что иначе разъехалось бы между двумя кадрами: положение и
поворот камеры, направление солнца, цвет и сила неба, время суток и
время кадра (трава качается по `fogParams.w`).

### Изоляция стенда

Сцена считается пригодной, только если в ней ничего не шевелится само.
Иначе два кадра нельзя сравнить, а расхождение нельзя приписать
рендеру.

При `debug_scene = true` в `update()` стоит единственная развилка, и
она ВЫХОДИТ из функции. После неё не выполняется ни одна игровая
система: ни ввод, ни физика игрока, ни смена суток, ни появление мобов
и NPC, ни их ИИ, ни предметы, ни снаряды, ни бой, ни задания, ни
прогресс, ни звук, ни автосейв. Остаётся ровно то, без чего сцены не
будет: подгрузка чанков вокруг неподвижной камеры.

Автосейв на выходе тоже отключён: записать ровную землю в слот
автосохранения значит затереть настоящий мир игрока.

У камеры в этом режиме ровно один владелец. `Camera::setDebugCamera`
прибивает её и поднимает признак, а `followTarget`, `setYawPitch`,
`setTargetPosition`, `setHeadBob`, `setFirstPersonEye`,
`setFirstPerson`, `setThirdPersonDistance` и `setThirdPersonHeight`
после этого молчат. Раньше отладочные значения ставились ДО
`followTarget`, и та пересчитывала положение заново — совпадение
держалось только на том, что рост глаз и тряска обнулены.

Шаг кадра и время мира постоянны: `SCENE_FIXED_DT = 1/60`,
`SCENE_TIME_SEC = 0`. Настоящий `dt` пляшет от загрузки телефона, а по
времени мира качается трава в шейдере.

Хост берёт солнце, небо, время и дальность из тех же констант и
ставит камеру тем же вызовом `setDebugCamera`. Второго владельца
камеры на хосте не осталось: матрица вида больше не собирается вручную
рядом с классом камеры, её считает `Camera::toUbo`.

Игра печатает доказательство изоляции раз в секунду, хост — один раз:

```
debug_scene=true кадр N | камера X Y Z, yaw .. pitch .. |
время мира .. , шаг кадра .. | мобы 0, NPC 0, предметы 0, снаряды 0 |
чанков загружено N, нарисовано M
```

Если хоть одно число поедет между кадрами, стенд негоден, и это видно
сразу, а не после сравнения картинок.

Проверка «сцена: стенд изолирован» держит всё перечисленное. Мутации
проверены: снятие заслона в `setYawPitch`, снятие `return` после
отладочного кадра и снятие заслона в `followTarget` роняют её каждая.

### Как получить два кадра

Эталон на хосте:

```
./tools/vkcheck/run.sh --scene minimal --viewdist 7 --size 2306 1080 --out build/vkcheck/scene_ref.ppm
```

На устройстве — в `settings.cfg`, раздел `[Render]`:

```
debug_scene = true
view_distance = 7
```

Пробелы вокруг «=» значения не имеют: разбор их обрезает. Раньше не
обрезал, и ровно этот пример молча не работал — ключ получался с
пробелом на конце и не совпадал ни с чем.

Дальность обязана совпасть с ключом `--viewdist`: по ней считаются и
туман, и границы уровней детализации.

Игра перезапускается, кадр снимается как есть.

### Как сравнить

```
./tools/vkcheck/compare.py build/vkcheck/scene_ref.ppm снимок.jpg --out разница.png
```

Скрипт снимает чёрные поля снимка, приводит его к размеру эталона и
печатает средний цвет семи областей: небо, земля вблизи, земля вдали,
лесенка, вода, крона и ствол дерева. Области выбраны так, чтобы не
попасть под кнопки интерфейса. Сравнение идёт по областям, а не по
отдельным пикселям: снимок пережат в JPEG, побайтовое совпадение
недостижимо и не нужно — нужно совпадение цветов поверхностей и
положения примет.

## Порядок проходов кадра

Раздел добавлен после разбора журналов с устройства (сборка `493e93e`,
экран 2306×1080). Всё, что здесь записано, получено замером; где
замера нет, так и сказано.

### Что сказал журнал

Главное наблюдение — одно, и оно решает всё остальное:

| сборка | нарисовано чанков | индексов | «рисование» |
|---|---|---|---|
| диагностическая | 63 | **1 884** | 19.5 мс |
| обычная | 66 | **154 380** | 19.1 мс |

Восемьдесят два раза больше геометрии дают ровно то же время. Значит
кадр упирается **не в вершины и не в число вызовов отрисовки**, а во
фрагменты или в постоянную стоимость кадра.

Оговорка про числа в журнале: строка «показано N (60.0/с)» в
диагностической сборке смысла не имеет. Там `dt` прибит к
`SCENE_FIXED_DT`, поэтому накопитель времени считает кадры, а не
секунды, и делённое на него всегда даёт около шестидесяти. Настоящая
частота — отдельный счётчик `FPS=`, и он показывает 45–50 в обеих
сборках.

### Что было не так

Самый большой фрагментный проход в кадре — небо: полноэкранный
треугольник, и он рисовался **первым**, с выключенной проверкой
глубины. То есть его шейдер считался для каждого пикселя экрана,
включая те, которые через несколько вызовов закрывал ландшафт.

Стоимость измерена (`tools/gpubench`, кадр 2306×1080):

| проход | время | на пиксель |
|---|---|---|
| ровная заливка (растр и запись) | 0.79 мс | 0.32 нс |
| шейдер неба | 7.99 мс | 3.21 нс |
| **собственно небо** | **7.20 мс** | **10.1× к заливке** |

Доля выброшенной работы измерена на кадре `tools/vkcheck`: 323 777
пикселей геометрии из 504 000, то есть **64% экрана**.

Считает `llvmpipe` — программный растеризатор на процессоре.
Абсолютные миллисекунды к телефону **не переносятся**; переносится
отношение между проходами и доля лишней работы. Именно за этим сюда и
ходят.

Вторая беда того же порядка: вода рисовалась сразу за непрозрачным
ландшафтом, то есть **до** мобов, NPC, предметов и травы. Вода не
пишет глубину — иначе смешивание не складывается, — поэтому любая из
этих сущностей, стоящая под водой, проходила проверку глубины и
оказывалась нарисованной **поверх** водной глади.

### Как стало

```
ландшафт (непрозрачное) -> NPC, мобы, снаряды, предметы, трава
  -> НЕБО -> вода -> контур блока -> интерфейс
```

Небо получило `depthTest = true, depthWrite = false`, а его вершинный
шейдер и так клал `z = 1.0` — дальнюю плоскость. При сравнении
`LESS_OR_EQUAL` оно проходит ровно там, где глубина осталась
очищенной, а закрытые ландшафтом пиксели отбрасываются до фрагментного
шейдера.

`ChunkRenderer::render` разделён на `renderOpaque` и `renderBlended`:
между ними обязаны встать сущности и небо. Отбор и отсечение по
пирамиде видимости делает `renderOpaque` — один раз на кадр, как и
раньше.

Проверка: `testFramePassOrder` в `tools/hostcheck/tests.cpp` сверяет
порядок как порядок (по взаимному положению вызовов), а не как
наличие строк, и заодно состояние глубины у неба. Проверена мутациями:
небо обратно первым — падает шесть проверок; вода обратно перед
сущностями — две; выключить проверку глубины у неба — одна.

### Чего этот разбор НЕ измерил

Время кадра на самом устройстве по-прежнему не разложено: «рисование»
в сводке меряется вокруг `beginFrame`/`endFrame`, а внутри `beginFrame`
стоит ожидание забора и `vkAcquireNextImageKHR`, то есть ожидание
экрана. В одном числе слиты «GPU занят» и «мы ждём вертикальную
синхронизацию».

Поэтому в сводку добавлены три величины: **ожидание экрана**, **запись
команд** и **GPU** — последняя по меткам времени самого GPU
(`VK_QUERY_TYPE_TIMESTAMP`) вокруг командного буфера кадра. Устройство
может меток не давать; тогда в строке стоит `GPU нет:0.0`.

Следующий запуск на устройстве отвечает на вопрос, на который этот
разбор ответить не мог: сколько GPU рисует на самом деле и насколько
его разгрузил новый порядок проходов.

## Что показали метки времени GPU

Первый запуск с новой сводкой (сборка `a9a936d`, экран 2306×1080,
метки времени есть: 52.1 нс на такт).

| | до порядка проходов (`493e93e`) | после (`a9a936d`) |
|---|---|---|
| диагностическая, «рисование» | 19.5 мс | **16.5 мс** |
| диагностическая, FPS | 43–50 | **55–61** |
| обычная, «рисование» | 19.1 мс | **15.2 мс** |
| обычная, FPS | 36–48 | **54–62** |

Разложение, которого раньше не было:

| сборка | ожидание экрана | запись команд | **GPU** |
|---|---|---|---|
| диагностическая (1 884 индекса) | 14.4 мс | 2.1 мс | **13.7 мс** |
| обычная (154 380 индексов) | 13.5 мс | 1.7 мс | **12.6 мс** |

Два вывода, и оба важны для следующего шага.

**Первый: запись команд не при чём.** 1.7–2.1 мс на процессоре против
12.6–13.7 мс на GPU. Ни число вызовов отрисовки, ни отбор по пирамиде
видимости в узкое место не попадают, и трогать их незачем.

**Второй: GPU по-прежнему не зависит от геометрии.** Восемьдесят два
раза больше индексов дают на миллиметр МЕНЬШЕ времени. Более того,
диагностическая сцена — почти пустая по геометрии — оказывается
дороже: в ней ландшафт это несколько огромных плоских квадов, которые
закрывают почти весь экран. То есть кадр упирается в площадь
закрашивания, а не в вершины, и главный расход — фрагментный шейдер
вокселей на тех самых двух третях экрана.

Остаток работы неба после смены порядка — треть экрана вместо целого.

### Как мерить дальше

Пока частота упирается в экран, по ней нельзя сказать ничего о
запасе: шестьдесят кадров показывает и машина, которой хватает
впритык, и машина, которая успевает вдвое больше. Поэтому в меню
(«Настройки» → «Рендер») есть тумблер **«Без ограничения кадров»**, и
он включён по умолчанию.

Со снятым ограничением цепочка показа создаётся в режиме
`VK_PRESENT_MODE_IMMEDIATE_KHR` — он отдаёт ровно то, что машина
успевает, ценой разрыва кадра. `MAILBOX` тут не годится: разрывов он
не даёт, но и максимума не покажет — лишние кадры он просто
выбрасывает. Если устройство не умеет ни того ни другого, остаётся
`FIFO`, и об этом пишется в журнал.

Строка свопчейна в журнале называет выбранный режим прямо:

```
Свопчейн: 2306x1080, экран повёрнут на 90, просим preTransform нет,
          показ IMMEDIATE (без ограничения)
```

### Журнал в буфере обмена

При выходе из игры журнал целиком копируется в буфер обмена — файл при
этом остаётся на месте, как и был. Это избавляет от похода в Termux
ради чтения.

Длинный журнал не влезает в транзакцию Binder (предел — около
мегабайта на весь процесс), поэтому берётся начало (32 КБ: там условия
запуска — устройство, разрешение, режим показа) плюс хвост (до 256 КБ
всего: там то, на чём всё кончилось), а между ними отметка о пропуске.

Копирование идёт на выходе, пока приложение ещё на переднем плане:
часть прошивок молча отказывает фоновым в записи в буфер. Если не
вышло, в журнал пишется строка с причиной, а файл остаётся доступен
прежним путём.

## Воксельный вид: цвет блока, освещённость грани, форма

Задача была сформулирована как «перестроить мир под полноценную
voxel-графику: убрать зависимость от текстур, задать каждому блоку
простой базовый цвет, развести грани по оттенкам». Первое, что
выяснилось при чтении кода, — половина работы уже сделана и сделана
давно, а обещанной поломки нет.

### Чего в террейне не было изначально

Текстур. Ни одной. В `voxel.frag`, `voxel.vert`, `voxel_pipeline.cpp`
и `mesh_builder.cpp` нет ни `sampler`, ни `texture`, ни UV: вершина
террейна весит восемь байт и несёт упакованную позицию плюс четыре
байта цвета материала. Цвет берётся из `world::BlockDef`, у которого
есть отдельные поля для верха, бока и низа. Меширование жадное,
внутренние грани отсекаются, затенение углов и открытость неба
запечены в вершину.

То есть перевода «текстурного рендерера в бестекстурный» здесь не
требовалось. Требовалось убрать то, что налипло поверх.

### Что мешало на самом деле

Три вещи, все — во фрагментном шейдере и в реестре блоков.

**Цвет зависел от места, а не только от материала.** Поверх альбедо
стояли две подкраски:

```glsl
// волна по мировым координатам
float t = sin(vWorldPos.x*0.021 + sin(vWorldPos.z*0.013)*2.3)*0.5 + 0.5;
albedo *= mix(vec3(0.82,1.05,0.78), vec3(1.14,0.95,0.66), t);
// градиент по высоте
float hf = clamp((vWorldPos.y - 40.0)/70.0, 0.0, 1.0);
albedo *= mix(vec3(0.90,0.93,1.00), vec3(1.05,1.03,0.97), hf);
```

Один и тот же блок травы получал множитель от `(0.82, 1.05, 0.78)` до
`(1.14, 0.95, 0.66)` — по красному канале разброс в треть. В кадре это
видно прямо: соседние поляны выкрашены разным зелёным без всякой на то
причины в мире.

Замер по снимку кадра (ближняя полоса, где туман ещё не начался;
плитки 20×20, в каждой — только ярко освещённые верхние грани травы,
считается ОТТЕНОК `R/G`, потому что яркость законно меняют свет и
затенение углов, а оттенок — нет):

| | разброс `R/G` по плиткам | полный размах |
|---|---|---|
| было | ±0.0257 | 0.0706 |
| стало | ±0.0014 | 0.0089 |

Разброс оттенка одного и того же материала по кадру упал в
восемнадцать раз.

**Наклон по граням задавался в двух местах сразу.** В реестре блоков у
камня, песка, снега и руд верх был светлее бока, а бок светлее низа
(`148/134/124` у камня). И независимо от этого шейдер добавлял
полусферу: `skyVis = 0.5 + 0.5·N.y`, небо сверху, тёплое отражение
земли снизу. Две шкалы одной и той же величины: подправить контраст
граней было нельзя, не выясняя каждый раз, какая из двух половин
сейчас видна.

**Крапчатость по номеру вокселя** (`hash13`) убрали из шейдера ещё
раньше, а поля остались: `BlockDef::grain`, `BlockDef::biomeTint`, биты
28..31 упакованной вершины, их распаковка в `voxel.vert` и передача
дальше через `vInfo`. Вся цепочка выглядела рабочей и не делала ничего.

### Что сделано

**Один материал — один цвет.** `colorTop/colorSide/colorBottom`
различаются только там, где грани и правда из разного материала:
зелёная макушка на земляном боку у травы, светлый спил на тёмной коре
у дерева. У камня, песка, снега, льда, воды, лавы, листвы, руд и
породы три поля совпадают.

**Освещённость грани — одна таблица.** `FACE_LIGHT` в `voxel.frag`:

| грань | +X | −X | +Y | −Y | +Z | −Z |
|---|---|---|---|---|---|---|
| множитель | 0.76 | 0.76 | 1.00 | 0.50 | 0.88 | 0.88 |

Числа неравные попарно, а не только «верх ярче боков»: у куба в кадре
видно самое большее одну грань из каждой пары, и при равной
освещённости вертикальное ребро между ними исчезает — куб схлопывается
в плоский силуэт. Полусферу по нормали убрали: наклон теперь ровно
один.

**Руды перекрашены.** Крапчатость была тем, чем руда отличалась от
породы; при одном цвете на материал `IRON_ORE (152,148,150)` на
`STONE (148,150,158)` пропадал в стене начисто. Теперь у руды цвет
своего металла на весь блок: железо `(176,152,134)`, золото
`(204,174,84)`.

**Мёртвые поля убраны.** `grain` и `biomeTint` из `BlockDef`, два
аргумента из `packVoxelPos`, их распаковка из `voxel.vert`. Биты 28..31
вершины свободны; `vInfo` теперь просто номер грани.

**Освещение — одна модель на весь мир.** Террейн, трава и существа
стоят в одном кадре друг на друге, а считали свет по-разному: у травы
рассеянный свет брался от самого `skyLin`, у террейна — от
приглушённого к белому; солнце у существ было вдвое сильнее, чем у
земли под ними; туман на закате красил горизонт под травой не так, как
над ней. При этом `mob.frag` в комментарии утверждал обратное. Теперь
`voxel.frag`, `grass.frag` и `mob.frag` берут одни и те же числа, а
существа — ещё и ту же таблицу освещённости граней, выбранную по
нормали (модели собраны из кубов). Общего заголовка у этих шейдеров
нет: `glslc` собирает каждый файл сам по себе, и заводить механизм
включений ради семи чисел дороже, чем сверять их тестом. Сверяет тест
«шейдеры: мир освещён по одной модели».

**Что осталось и почему.** Фаска по краям клетки — потому что жадное
слияние отдаёт сотню блоков одним квадом, и без неё склон выходит
сплошной заливкой, в которой отдельных кубов не видно вовсе. Затенение
углов и открытость неба — они и дают объём и отделяют пещеру от
склона. Блик и Френель на воде — см. замер ниже.

### Цена

Фрагментный шейдер террейна, парный замер на одной машине, по три
прогона на вариант (`tools/gpubench`, полноэкранный проход
2306×1080, программный Vulkan):

| | прогоны, мс | лучший |
|---|---|---|
| было | 6.33 / 6.62 / 6.33 | 6.33 |
| стало | 5.95 / 5.94 / 5.95 | 5.94 |

−6 % на фрагмент; при доле террейна в кадре 64 % это −0.24 мс.
Скомпилированный SPIR-V: 2810 → 2321 слов (−17 %). Двух вызовов `sin`
на фрагмент не стало вовсе.

Абсолютные миллисекунды здесь считает процессор (lavapipe) и на телефон
не переносятся; переносится отношение и размер шейдера.

**Ветка воды измерена отдельно, а не выброшена на глаз.** У
`tools/gpubench` появился второй зонд — тот же фрагментный шейдер, но
грань подаётся полупрозрачной, и ветка с бликом `pow64` и Френелем
`pow4` исполняется:

| проход | мс на полный экран |
|---|---|
| грань террейна | 5.99 |
| грань воды | 7.65 |
| ветка блика и Френеля | 0.96 (+16 %) |

Ветка динамическая и работает только на пикселях воды и льда. При
доле воды в кадре даже в пятую часть экрана это 0.19 мс — за то, что
вода перестаёт читаться как синее стекло на дне. Оставлено.

### Геометрия не изменилась вовсе

Мешер не тронут. Один и тот же кадр до и после:

```
чанков 441, квадов 86374, мешей 441
по уровням: 0:37 1:75 2:190 3:139
пикселей геометрии: 365596
сообщений слоя проверки: 0
```

Числа совпадают до единицы — сменился только цвет (средняя яркость
нижней половины кадра 0.438 → 0.436).

### Чем это закреплено

| тест | что ловит | проверено мутацией |
|---|---|---|
| «цвет грани зависит только от материала и грани» | возврат шума, волны по координатам, градиента по высоте | вернул `sin(vWorldPos.x)` в альбедо — падает |
| «освещённость грани: один источник истины» | второй наклон в реестре блоков или полусфера в шейдере; руда, слившаяся с камнем | вернул камню светлый верх — падает; вернул руде цвет камня — падает |
| «мир освещён по одной модели» | расхождение чисел между `voxel.frag`, `grass.frag`, `mob.frag` | вернул траве солнце 0.62 — падает |
| «стык чанков через начало координат» | грани внутри земли на стыке, дыры в покрытии, стена по неизвестному соседу | сломал чтение соседа по −X — падает; убрал различение `UNKNOWN` — падает |

### Что проверено глазами

Снимки `tools/vkcheck` (настоящий Vulkan, те же `.spv`, слой проверки
включён, ноль сообщений) до и после, одинаковые камеры:

* обычный склон с террасами, полдень;
* сутки целиком — у инструмента появился ключ `--time`, который берёт
  солнце и цвет неба из того же `world::DayCycle`, что и игра;
  проверены 0.22, 0.35, 0.50, 0.78, 0.90 — ночь не потемнела;
* озеро с водой и песчаным берегом — вода не изменилась;
* дальний вид с уровнями 0..3 в одном кадре — дыр и висящих плит нет,
  силуэт читается.

### Чего инструмент не показывает

`tools/vkcheck` не рисует небо шейдером: он про геометрию и свет
террейна, и лишний полноэкранный проход мешал бы считать пиксели. Фон
— заливка. Раньше заливка была постоянной, и ночной снимок выходил с
дневным небом; теперь при `--time` она берёт цвет неба этого времени
суток. Само `sky.frag` по-прежнему проверяется только на устройстве и
в `tools/gpubench`.
