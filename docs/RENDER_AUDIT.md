# Разбор пути отрисовки: от вокселя до кадра на экране

Карта построена по ИСХОДНОМУ КОДУ и по КАРТИНКЕ С УСТРОЙСТВА.
Комментарии, прежние проверки и прежние выводы источником истины
не считаются: там, где комментарий расходится с кодом, записан код;
там, где код расходится с картинкой, записана картинка.

Состояние на коммит `fb87bda`, ветка `claude/project-full-review-4757sr`.
Устройство: 2306×1080, экран повёрнут на 90°, `depth=126`
(`VK_FORMAT_D32_SFLOAT`), слоя проверки на устройстве нет.

Обозначения в графах: **СК** — система координат, **Y** — куда растёт
Y, **обход** — порядок вершин лицевой грани, **влад.** — кто владеет
памятью и сколько она живёт.

| выход | `world::Chunk::voxels` — `std::array<u16, 131072>` |

| индекс | `(y * 32 + z) * 32 + x`, `chunk.h:24` |
| СК | локальная для чанка: `x,z ∈ [0,32)`, `y ∈ [0,128)` |
| единицы | 1 воксель = 1 блок = 1 мировая единица |

Мировая координата: `world = coord.x * 32 + x`. Пула чанков нет,

## 2. Жадное меширование — `world::buildGreedyMeshInto`, `chunk.cpp:322`

| | |
|---|---|
| вход | `Chunk` + `ChunkNeighbors` (4 соседа по X/Z, **любой может быть `nullptr`**) |
| выход | `std::vector<world::Quad>` / `std::pmr::vector<Quad>` |
| СК | КЛЕТКИ выбранного уровня, перевод в блоки один раз при записи квада |
| единицы | клетка = `step = 1 << lod` вокселей: 1, 2, 4, 8 |
| обход | здесь ещё нет — квад хранится как `origin + du + dv` |
| нормаль | `q.v0.face`, индекс 0..5 в порядке `+X, −X, +Y, −Y, +Z, −Z` |
| влад. | арена воркера (`mem::Arena`, thread_local), затем копия в `chunk.meshes[lod].quads` |
| синхр. | `shared_lock` на свой чанк и на всех ненулевых соседей, захват в порядке возрастания адреса; результат под `chunk.meshMutex` |

Оси граней (`FACES`, `chunk.cpp:52`):

| грань | u | v | w | знак |
|---|---|---|---|---|
| +X, −X | Y | Z | X | +1 / −1 |
| +Y, −Y | X | Z | Y | +1 / −1 |
| +Z, −Z | X | Y | Z | +1 / −1 |

Начало квада: `org[w] = (slice + (sign > 0 ? 1 : 0)) * step`,
`org[u] = iu * step`, `org[v] = iv * step`;
`du[u] = wU * step`, `dv[v] = wV * step`.

Затенение и небо считаются в клетке **перед** гранью (`n = c + sign`
по оси w) — то есть в воздухе, а не в теле блока. Для верхней грани
это даёт открытость 7. Журнал устройства это подтверждает: у верхних
граней доля открытых 0.95..1.00.

Слияние требует совпадения блока, AO и неба разом — иначе тень свода
растеклась бы по освещённому склону.

## 4. Упаковка вершин — `render::emitQuad`, `mesh_builder.cpp:35`

| | |
|---|---|
| вход | `Quad` + `BlockDef` |
| выход | `VoxelVertex{ u32 packed; u8 r,g,b,a; }` — 8 байт |

## 5. Загрузка через staging — `ChunkRenderer::uploadLod`, `chunk_renderer.cpp:78`

| | |
|---|---|
| вход | `scratchVerts_` / `scratchIndices_` |
| выход | копия в device-local буфер |
| индекс | `u16`, если вершин ≤ 65535, иначе `u32`; тип пишется в `gm.indexType` |
| влад. | `vk::StagingPool` — буфер занят `TRANSFER_SLOTS` пакетов после `retire()` |
| синхр. | барьер `VERTEX_INPUT → TRANSFER` в начале пакета и `TRANSFER → VERTEX_INPUT` в конце; `beginTransferBatch` ждёт забор слота перед переиспользованием командного буфера |

Время жизни staging сходится: буфер, отданный в пакете N, помечается
свободным при `collect()` кадра N+K, а `beginTransferBatch` того же
кадра ждёт забор пакета N до того, как `acquire()` его выдаст.

| | |
|---|---|

## 10. Фрагментный шейдер террейна — `voxel.frag`

| | |
|---|---|
| точность | `precision mediump float; precision mediump int;` — на мобильном GPU это fp16 |
| highp явно | `vWorldPos`, `cell`, `fp`, `f`, `d`, `hash13`, `toFrag`, `V` |
| **mediump по умолчанию** | **весь блок `CameraUbo`, включая `cameraPos` и `viewProj`**, а также `vColor`, `vShade` |
| нормаль | `FACE_N[face]`, `face` из `flat uint` — плоская, per-primitive |
| зерно | `hash13(floor(vWorldPos − N*0.5))`, период ровно 1 блок, размах `±grain/2 ≤ ±15 %` |
| фаска | `fract` от мировых координат, только ЗАТЕМНЯЕТ, диапазон `[0.84, 1.0]` |
| свет | полусфера (небо сверху, отражение земли снизу) × AO × открытость неба + солнце |
| туман | по расстоянию, `smoothstep`, цвет неба с подмесом солнца |

Проверено численно: `ambient` для верхней грани при открытом небе
даёт множитель ≈0.63..0.86, ни одно слагаемое не может дать резкий
светлый прямоугольник в четверть блока (см. п. 21).

## 13. Отсечение граней

Геометрия всюду намотана против часовой стрелки при взгляде снаружи:
таблицы кубов (`CUBE_I` в мобах, NPC, предметах) и мешер чанков.

## Найденные противоречия

### П1. Порядок каналов цвета у всех инстансных кубов — ПОДТВЕРЖДЁН

Процессор складывает цвет как `0xRRGGBBAA`:

```cpp
// mob_def.cpp:11
constexpr u32 rgb(u8 r, u8 g, u8 b) {
    return ((u32)r << 24) | ((u32)g << 16) | ((u32)b << 8) | 0xFF;
}
// item_renderer.cpp:58
case items::ItemRarity::Uncommon: return 0x60D060FF;
```

Видеокарта читает те же четыре байта **в порядке памяти**:

```cpp
{ 3, 1, VK_FORMAT_R8G8B8A8_UNORM, 24 },   // iColor
```

На порядке байтов от младшего (ARM, x86) `u32 0xRRGGBBAA` лежит в
памяти как `AA BB GG RR`. Значит шейдер получает
**R = A, G = B, B = G, A = R**. Никакого обратного перестроения нет:
`mob.vert` делает `vColor = iColor;`, `mob.frag` — `toLinear(vColor.rgb)`
и `outColor.a = vColor.a`.

Последствия:

* тело коровы `rgb(80,60,40)` — тёмно-коричневое — приходит в шейдер
  как **(255, 40, 60)**, ярко-красное. На снимке с устройства на
  тёмном склоне действительно видны ярко-красные и малиновые
  прямоугольники там, где стоят мобы;
* у всех цветов редкости предметов `AA = FF`, значит **R = 1.0** у
  каждого выпавшего предмета;
* альфа берётся из байта R. Для непрозрачных проходов это почти
  безобидно, но конвейер снарядов объявлен со смешиванием — там
  прозрачность получается произвольной.

Затронуты: `mob_renderer`, `npc_renderer`, `item_renderer`,
`projectile_renderer`. **Не затронуты** террейн (`emitQuad`
распаковывает байты вручную) и трава (`GrassInstance` хранит
отдельные `u8 r, g, b, a`).

То есть в проекте сосуществуют два несовместимых соглашения о цвете, и
ни одна проверка их не сличала.

### П6. Точность межстадийных переменных не совпадает — ПОДТВЕРЖДЕНО В SPIR-V

`voxel.vert` не объявляет точности вовсе, то есть по умолчанию весь он
`highp`: в скомпилированном модуле **ноль** декораций
`RelaxedPrecision`. `voxel.frag` начинается с
`precision mediump float; precision mediump int;` — в нём таких
декораций **340**. Разошлись ровно межстадийные переменные:

| переменная | вершинный | фрагментный |
|---|---|---|
| `vColor` (0) | нет (highp) | **RelaxedPrecision** |
| `vWorldPos` (1) | нет | нет — совпадает |
| `vShade` (2) | нет (highp) | **RelaxedPrecision** |
| `vInfo` (3) | нет (highp) | **RelaxedPrecision** |

Три переменные из четырёх объявлены в двух стадиях с разной точностью.
Правила стыковки интерфейсов в Vulkan сверяют тип и расположение, а
декорацию точности — нет, так что модуль проходит проверку; но хранит
и передаёт такую переменную драйвер по своему усмотрению.

Важно, ЧТО именно разошлось: `vShade` — это запечённые затенение углов
и открытость неба, и множители освещения из них не ограничены сверху:

```glsl
float ao  = 0.42 + 0.58 * vShade.x;
float sky = 0.18 + 0.82 * vShade.y;
```

Пока `vShade` лежит в [0,1], множитель не выходит за единицу. Стоит
значению уехать — освещение уезжает вместе с ним в обе стороны, без
всякого предела.

Именно это и видно на устройстве. Снимок 2400×1080, обычный мир, зерно
12648430, камера 4.5 34.0 −0.7:

* **46 %** кадра имеет хотя бы один канал, упёртый в 255 (зелёный в
  34 %, красный в 12 %);
* **18 %** кадра — чистый чёрный;
* небо при этом правильное: (125,168,236) — его рисует другой шейдер.

Тот же шейдер, то же зерно и та же камера на хосте дают землю
**(112,177,74)** — ровно то, что предсказывает формула. На устройстве в
этом прогоне **(178,255,125)**, в прогоне до этого — **(54,80,32)**.
Формула не может дать ни того, ни другого: `shoulder` упирает
максимальный канал в 1.25, а для насыщения зелёного нужен множитель
света около 2.4 при потолке формулы 0.9.

ЧЕГО ЭТО НЕ ДОКАЗЫВАЕТ. Половинная точность сама по себе уже
проверена и отброшена: кадр, нарисованный после
`spirv-opt --convert-relaxed-to-half`, отличается от обычного не более
чем на 3 из 255. То есть дело не в том, что 16 бит мало для чисел
0..1, — а в том, что переменная объявлена по-разному в двух стадиях.
Проверить это можно только на устройстве: программная реализация
Vulkan декорацию игнорирует и считает всё в 32 битах, поэтому хост
расхождение не воспроизводит по построению.

### П2. Вьюпорт и ножницы задаются не всеми проходами

Трава и контур блока полагаются на динамическое состояние, выставленное
предыдущим проходом. Динамическое состояние не наследуется между
командными буферами, и порядок проходов — единственное, что сейчас
удерживает это от неопределённого поведения. Слоя проверки на
устройстве нет, поэтому предупреждения об этом никто не увидит.

### П3. Вода рисуется до мобов, предметов, снарядов и травы

Вода читает глубину, но не пишет её. Всё, что нарисовано после неё и
находится ЗА ней, пройдёт тест глубины по дальнему непрозрачному
фону и ляжет поверх воды.

### П4. Комментарий о повороте расходится с кодом

`camera.h` говорит «мы пообещали композитору поворот через
preTransform, значит поворачиваем содержимое сами», а
`vk_context.cpp` просит `IDENTITY` и оставляет поворот композитору.
Ветка доворота в проекции на этом устройстве мертва. Расхождение
документации, не поведения, но именно оно уже стоило одного круга.

### П5. Соседи при меширования могут быть `nullptr`

`gatherNeighbors` возвращает то, что загружено; `sampleVoxel`
подставляет `AIR` за отсутствующего соседа. Пересборки меша при
появлении соседа не происходит, если не менялась `version` чанка.
Затрагивает только одно кольцо блоков на стыке чанков, то есть
объяснить решётку с шагом в один блок не может, но остаётся
несоответствием между «данные полные» и «данные какие есть».

**Закрыто.** `sampleVoxel` отдаёт `UNKNOWN`, мешер по такой границе
грань не строит, а появление соседа ставит стык на перемешивание.

### П7. Уровень детализации выбирали двое, и по разным меркам

Мир (`ChunkManager::jobGenerate`) мерил расстояние от чанка ИГРОКА до
чанка в квадратах чанков; рендер (`ChunkRenderer::render`) — от КАМЕРЫ
до центра чанка в блоках. Величины разные, границы уровней у каждого
свои, мёртвая зона была только у рендера. У границы стороны спорили
каждый кадр: мир строил один уровень, рендер тут же заказывал другой.

К этому прилагались три отдельных механизма, каждый со своим
последствием:

* задача меширования выбрасывала ВСЕ прочие уровни чанка, как только
  бралась строить новый, — включая тот, который сейчас на экране;
* рендер, не найдя нужного уровня, брал первый попавшийся из четырёх, а
  набор «попавшихся» менялся сам по себе;
* самый грубый уровень (шаг 8) начинался на 0.90 дальности, а туман
  кончался на 0.94 — девять процентов дальности самой грубой геометрии
  были видны у горизонта.

**Закрыто.** Формула одна на весь проект (`world/lod.h`), считается от
позиции камеры, с мёртвой зоной у обеих сторон; резидентный уровень
живёт до успешной загрузки нового и служит единственным запасным
вариантом; грубейший уровень уведён за конец тумана.

### П8. Прозрачное сортировалось по центру чанка

Проход со смешиванием шёл в обратном порядке непрозрачного, то есть по
расстоянию до ЦЕНТРА чанка — а тот лежит на половине высоты мира, в
шестидесяти с лишним блоках над водой. Порядок выходил почти
случайный. Сюда же — огрубление воды: клетка 8³ доставалась верхнему
вокселю, и берег шириной в полклетки становился прозрачным, а озеро
под одиноким выступом исчезало целиком.

**Закрыто.** Меш хранит центр своей прозрачной геометрии, взвешенный
по площади граней; проход со смешиванием сортируется отдельным
списком по нему. Огрубление решает по колонкам: клетка становится
водой, только если вода наверху у большинства колонок.

### П9. pow() с нулевым основанием — ПОДТВЕРЖДЁН НА УСТРОЙСТВЕ

Вся геометрия дальше начала тумана рисовалась угольно-чёрной. Граница
чёрного совпадала с границей тумана попиксельно: кадры устройства и
хоста, совмещённые по приметам сцены, расходятся на два пикселя, и
ровно там, где на хосте туман перестаёт быть нулевым, на устройстве
начинается чёрное. Ближе — картинка верная, дальше — чёрное до самого
края мира. В нескольких пикселях внутри чёрного, наоборот, светлее
неба.

`pow(x, k)` везде считается как `exp2(k * log2(x))`, и при `x = 0` это
`log2(0) = -inf`. Что выйдет дальше — дело драйвера. Основание здесь
обнуляется постоянно:

    float sunAmt   = max(dot(normalize(toFrag), cam.sunDir.xyz), 0.0);
    vec3  fogColor = mix(skyLin, sunTint, pow(sunAmt, 8.0) * 0.30 * above);

`max(dot(...), 0.0)` равен нулю для любого фрагмента, отвёрнутого от
солнца, — то есть для половины кадра. Результат уходил в цвет тумана, а
`toSrgb` со своим `max(c, 0.0)` превращал его в ноль.

Три независимых свидетельства:

* `voxel.frag` — ЕДИНСТВЕННЫЙ шейдер проекта, объявленный
  `precision mediump float`, и единственный, где виден артефакт.
  `grass.frag` и `mob.frag` считают ровно ту же формулу тумана с тем же
  `pow(sunAmt, k)`, но в полной точности — и трава с мобами на том же
  кадре нарисованы верно.
* Второй `pow` в `voxel.frag` стоит в ветке для полупрозрачного — блик
  и Френель на воде. На кадре устройства чёрным залито и пятно воды.
* Программный Vulkan (lavapipe, fp32) на той же сцене даёт правильный
  туман: `pow(0, k)` там ноль, и артефакт не воспроизводится по
  построению.

**Закрыто.** В `voxel.frag` не осталось ни одного `pow`: показатели 8,
64 и 4 — степени двойки, они раскладываются умножениями (точнее и
дешевле). Весь расчёт тумана объявлен `highp`, вес подмешивания и
итоговый цвет ограничены своими диапазонами. В остальных шейдерах
основание подпирается снизу через `powSafe`. Заодно исправлен
`smoothstep(0.0, -0.25, up)` в `sky.frag`: `edge0 >= edge1` по
спецификации не определено.

## Что противоречиями НЕ объясняется

Главный видимый артефакт — решётки светло-зелёных прямоугольников
поверх уже отрисованного ландшафта. Измерено по снимку 2400×1080:

* размер метки 4..8 пикселей по обеим осям, **не зависит от глубины**:
  медиана высоты 3 пикселя и у горизонта, и под ногами;
* шаг решётки совпадает с шагом сетки блоков в том же месте кадра
  (автокорреляция чистой земли на `y = 880` даёт период 32 пикселя,
  метки там же стоят через 32 пикселя) — **одна метка на блок**;
* метка — прямоугольник с резкой границей примерно в четверть блока,
  в одном и том же месте каждого блока;
* **цвет метки постоянен и не зависит от подложки**: по 583 меткам
  фон меняется от (45,63,26) до (55,83,37), метка везде (100,213,137).
  Значит это отдельный материал, а не подсветка поверхности;
* меток порядка 550, тогда как трава в том же кадре — 104 пучка;
* над чистым небом меток нет (2 пикселя на 68 тысяч) — значит
  геометрия с тестом глубины, а не наложение поверх кадра.

Проверено и отброшено: трава (радиус 40 блоков, пучок на предельной
дистанции занимает 21 пиксель — метки в 4 пикселя не бывает; и метки
не изменились, когда лист сузили втрое), затенение (журнал показывает
открытость неба 0.95..1.00), половинная точность (кадр, нарисованный
настоящим fp16 после `spirv-opt --convert-relaxed-to-half`, отличается
от обычного не более чем на 3 из 255), дальние уровни детализации
(радиус проверки поднят до дальности прорисовки, 225 чанков,
уровни 16/40/64/105 — меток нет), разрешение и пересжатие снимка.

Ни одно слагаемое `voxel.frag` не способно дать резкий светлый
прямоугольник в четверть блока: зерно постоянно на целый блок и
ограничено ±15 %, фаска только затемняет и ограничена 0.84,
подкраска и высота меняются плавно.

**Вывод: артефакт не воспроизводится ничем, что доступно на хосте, и
не объясняется ни одним слагаемым шейдера террейна. Следующий шаг —
минимальная детерминированная сцена, одинаковая на хосте и на
устройстве, и сравнение кадров.**

## Минимальная детерминированная сцена

Строит её одна функция — `world::buildMinimalScene`
(`app/src/main/cpp/src/world/debug_scene.cpp`), — а рисуют оба
рендера. Сцена не зависит ни от зерна мира, ни от шума, ни от порядка
загрузки соседей; повторная сборка даёт тот же чанк до последнего
вокселя (проверяется в hostcheck).

Содержимое (нулевой чанк, приметы в блоках):

| примета | где |
|---|---|
| ровная земля | камень до y=28, земля 28..30, трава на y=31; верх — y=32 |
| один поднятый блок | камень в (8, 32, 20) |
| одна лесенка | x 12..19, z 4..11, высота растёт на блок за шаг |
| одна вода | x 22..29, z 16..23; дно камень на y=29, вода 30..31, верх вровень с землёй |
| одно дерево | ствол (5, 32..35, 6), крона 5×5×3 со срезанными углами |
| трава | по тому же хешу, что в игре, от высоты `SCENE_GROUND_Y` |
| небо | обычный проход неба |
| игрок | камера в (16.5, 44.0, −18.0), yaw 0, pitch −0.50 |

Соседние чанки — та же ровная земля: они дают центральному честных
соседей, и на стыках нет швов.

Прибито всё, что иначе разъехалось бы между двумя кадрами: положение и
поворот камеры, направление солнца, цвет и сила неба, время суток и
время кадра (трава качается по `fogParams.w`).

### Изоляция стенда

Сцена считается пригодной, только если в ней ничего не шевелится само.
Иначе два кадра нельзя сравнить, а расхождение нельзя приписать
рендеру.

При `debug_scene = true` в `update()` стоит единственная развилка, и
она ВЫХОДИТ из функции. После неё не выполняется ни одна игровая
система: ни ввод, ни физика игрока, ни смена суток, ни появление мобов
и NPC, ни их ИИ, ни предметы, ни снаряды, ни бой, ни задания, ни
прогресс, ни звук, ни автосейв. Остаётся ровно то, без чего сцены не
будет: подгрузка чанков вокруг неподвижной камеры.

Автосейв на выходе тоже отключён: записать ровную землю в слот
автосохранения значит затереть настоящий мир игрока.

У камеры в этом режиме ровно один владелец. `Camera::setDebugCamera`
прибивает её и поднимает признак, а `followTarget`, `setYawPitch`,
`setTargetPosition`, `setHeadBob`, `setFirstPersonEye`,
`setFirstPerson`, `setThirdPersonDistance` и `setThirdPersonHeight`
после этого молчат. Раньше отладочные значения ставились ДО
`followTarget`, и та пересчитывала положение заново — совпадение
держалось только на том, что рост глаз и тряска обнулены.

Шаг кадра и время мира постоянны: `SCENE_FIXED_DT = 1/60`,
`SCENE_TIME_SEC = 0`. Настоящий `dt` пляшет от загрузки телефона, а по
времени мира качается трава в шейдере.

Хост берёт солнце, небо, время и дальность из тех же констант и
ставит камеру тем же вызовом `setDebugCamera`. Второго владельца
камеры на хосте не осталось: матрица вида больше не собирается вручную
рядом с классом камеры, её считает `Camera::toUbo`.

Игра печатает доказательство изоляции раз в секунду, хост — один раз:

```
debug_scene=true кадр N | камера X Y Z, yaw .. pitch .. |
время мира .. , шаг кадра .. | мобы 0, NPC 0, предметы 0, снаряды 0 |
чанков загружено N, нарисовано M
```

Если хоть одно число поедет между кадрами, стенд негоден, и это видно
сразу, а не после сравнения картинок.

Проверка «сцена: стенд изолирован» держит всё перечисленное. Мутации
проверены: снятие заслона в `setYawPitch`, снятие `return` после
отладочного кадра и снятие заслона в `followTarget` роняют её каждая.

### Как получить два кадра

Эталон на хосте:

```
./tools/vkcheck/run.sh --scene minimal --viewdist 7 --size 2306 1080 --out build/vkcheck/scene_ref.ppm
```

На устройстве — в `settings.cfg`, раздел `[Render]`:

```
debug_scene = true
view_distance = 7
```

Дальность обязана совпасть с ключом `--viewdist`: по ней считаются и
туман, и границы уровней детализации.

Игра перезапускается, кадр снимается как есть.

### Как сравнить

```
./tools/vkcheck/compare.py build/vkcheck/scene_ref.ppm снимок.jpg --out разница.png
```

Скрипт снимает чёрные поля снимка, приводит его к размеру эталона и
печатает средний цвет семи областей: небо, земля вблизи, земля вдали,
лесенка, вода, крона и ствол дерева. Области выбраны так, чтобы не
попасть под кнопки интерфейса. Сравнение идёт по областям, а не по
отдельным пикселям: снимок пережат в JPEG, побайтовое совпадение
недостижимо и не нужно — нужно совпадение цветов поверхностей и
положения примет.
