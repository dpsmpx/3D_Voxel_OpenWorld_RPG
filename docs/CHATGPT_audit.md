## HIGH — сохранённые дельты мира могут быть затёрты генерацией чанка

Файлы:
- app/src/main/cpp/src/save/world_delta.cpp — WorldDeltaStore::applyAll()
- app/src/main/cpp/src/world/chunk_manager.cpp — getChunk(), jobGenerate()
- app/src/main/cpp/src/main.cpp — makeWorld(), doLoad()

Механизм:

1. doLoad() создаёт мир через makeWorld(meta.seed).
2. makeWorld() создаёт новый ChunkManager, но игровые чанки ещё не сгенерированы.
3. WorldDeltaStore::applyAll() для каждого сохранённого чанка вызывает world.getChunk().
4. getChunk() создаёт пустой Chunk и сразу отправляет его в enqueueGenerate().
5. applyAll() тем временем записывает сохранённые блоки в этот чанк.
6. jobGenerate() затем под voxelMutex вызывает generateChunkVoxels(), то есть записывает весь массив voxels заново.
7. В генераторе нет механизма повторного применения world delta после генерации.

Результат: модификации удалённых/ещё не сгенерированных чанков могут исчезнуть после загрузки сохранения.

Как исправлять: дельты должны применяться после завершения генерации либо быть частью атомарной стадии generate -> apply saved delta -> publish generated.

## HIGH — смерть уничтожает часть золота свыше 19 999

Файл: app/src/main/cpp/src/player/player.cpp, Player::tickDeath()

Текущий код вычисляет половину потерянного золота в u64, списывает всю сумму, но в ItemStack кладёт максимум 9999.

При 30 000 золота:
- списывается 15 000;
- на землю помещается только 9 999;
- 5 001 золота исчезает навсегда.

Это не просто UI-проблема: экономика игрока теряет валюту.

Как исправлять: дробить потерянные монеты на несколько стеков/подбирать другое представление валютного pickup.

## HIGH — сырой ECS ID NPC сохраняется в сейве и становится недействительным после перезапуска

Файл: app/src/main/cpp/src/save/save_player.cpp, writeQuest()/readQuest()

В сохранение задания пишутся runtime ECS IDs:

    q.giverEntity
    q.ownerEntity

giverEntity — обычный EnTT entity ID NPC.

При загрузке новые сущности создаются заново. NPC прошлого процесса с тем же runtime ID не восстанавливаются как тот же объект. Позже ID могут быть переиспользованы другой сущностью.

В dialogue.cpp сохранённый giverEntity используется для связи сдачи квеста с деревней:

    reg.get<ecs::Transform>(q->giverEntity)
    world::lightVillageDeed(world, v)

Результат: после перезапуска активный квест может потерять исходного NPC, а связанное с ним последствие в мире — не сработать.

Как исправлять: сохранять стабильный persistKey NPC/места, а runtime ECS ID разрешать заново после загрузки.

## HIGH — повреждённый WorldDelta может вызвать выход за границы массива

Файл: app/src/main/cpp/src/save/world_delta.cpp

WorldDeltaStore::read() читает m.index, но не проверяет, что индекс помещается в один чанк.

После чтения индекс попадает в decodeIndex(), затем applyAll() делает запись:

    c->voxels[linearIndex(lx, ly, lz)] = m.block;

Для индекса за пределами CHUNK_VOLUME декодированный ly может выйти за CHUNK_SIZE_Y и запись уйдёт за границы voxels.

CRC защищает от случайного повреждения, но не от заранее сформированного файла с корректной CRC.

Как исправлять: проверять m.index < CHUNK_VOLUME при чтении и дополнительно защищать applyAll().

## HIGH — ошибка записи meta не влияет на результат SaveManager::save()

Файл: app/src/main/cpp/src/save/save_manager.cpp

В конце save():

    slot.writeMeta(meta);
    LOGI("Save OK: ...");
    return SaveStatus::Ok;

Возвращаемое значение writeMeta() игнорируется.

Если .vxs записался, а .meta нет:
- save() сообщает Ok;
- лог сообщает Save OK;
- scanAll()/continueWorld() требуют оба файла;
- слот может фактически стать недоступным для продолжения.

Как исправлять: проверять результат writeMeta() и возвращать WriteError при неудаче.

## HIGH — основной файл сохранения записывается неатомарно

Файл: app/src/main/cpp/src/save/save_manager.cpp

Живой .vxs файл открывается напрямую через fopen(path, "wb"), затем заголовок и тело записываются последовательно.

Убийство Activity, падение процесса, сбой накопителя или прекращение записи между этими шагами может оставить обрезанный сейв.

Дополнительный риск даёт независимая запись .meta.

Как исправлять: писать во временный файл, успешно завершать запись и затем атомарно заменять предыдущий файл; желательно иметь предыдущую гарантированно целую копию.

## HIGH — неуспешная загрузка может частично изменить уже живое состояние игры

Файлы:
- app/src/main/cpp/src/save/save_manager.cpp
- app/src/main/cpp/src/save/save_player.cpp
- app/src/main/cpp/src/save/save_inventory.cpp
- app/src/main/cpp/src/save/world_delta.cpp

load() мутирует рабочий Registry поэтапно. Если поздний этап чтения завершится ошибкой, предыдущие изменения не откатываются.

Особенно наглядный случай — deserializePickups():

1. сначала уничтожаются все существующие pickups;
2. затем начинается чтение новых;
3. при ошибке чтения функция возвращает false.

То есть попытка загрузить повреждённый сейв может уничтожить текущие лежащие предметы, хотя сам load завершится статусом CorruptedData.

WorldDeltaStore::read() аналогично сначала делает deltas_.clear(), а затем может вернуть false посередине разбора.

Как исправлять: читать во временное состояние, валидировать целиком, после чего одним commit заменять live-state.

## MEDIUM — повторное восстановление исходного блока оставляет ложную world delta

Файл: app/src/main/cpp/src/save/world_delta.cpp, WorldDeltaStore::recordBlock()

Callback получает только конечный ID блока и всегда сохраняет запись. Нет сравнения с процедурным состоянием.

Сценарий:
1. A -> B;
2. B -> A;
3. delta остаётся со значением A.

Результат: чанк продолжает считаться модифицированным и сохраняется запись, которая уже совпадает с процедурным миром.

Как исправлять: сравнивать новый ID с детерминированным исходным блоком; при совпадении удалять BlockMod и пустой ChunkDelta.

## MEDIUM — сдача квеста не привязана к текущему NPC

Файл: app/src/main/cpp/src/npc/dialogue.cpp

choiceIsAvailable() разрешает CompleteQuest, если у игрока есть любой Completed-квест.

applyChoice() затем перебирает все активные квесты и сдаёт первый Completed.

Нет проверки вида:

    q.giverEntity == dlg.npcEntity

Результат: завершённое поручение NPC A можно сдать при разговоре с NPC B.

Это особенно заметно при наличии нескольких квестодателей или нескольких деревень.

Как исправлять: привязать turn-in к стабильному идентификатору исходного NPC либо явно описывать список разрешённых сдающих.

## MEDIUM — таймеры нескольких спавнеров зависят от FPS

Файлы:
- app/src/main/cpp/src/npc/npc_spawner.cpp
- app/src/main/cpp/src/crafting/crafting_station.cpp
- app/src/main/cpp/src/world/enchant_altar.cpp

В update() используется:

    timer += 1.f / 60.f;

вместо фактического dt.

Поэтому интервал в 0.75 секунды, 2 секунды и т.п. зависит от FPS устройства. При 45 FPS реальное время между событиями отличается от 60 FPS.

Как исправлять: передавать фактический dt во все эти update().

## MEDIUM — быстрые снаряды могут пролетать сквозь сущности

Файл: app/src/main/cpp/src/combat/projectile.cpp

Пересечение с блоками проверяется raycast-ом по всему шагу, но сущности проверяются только после полного переноса:

    tf->position += step;
    checkOneCandidate(... tf->position ...);

Если снаряд за один кадр прошёл через моба, но закончил кадр уже за ним, checkOneCandidate() не увидит пересечение.

Проблема особенно актуальна для высоких скоростей снарядов, включая зарегистрированные значения до 60 единиц/с.

Как исправлять: использовать swept sphere/capsule test по отрезку от старой позиции к новой.

## MEDIUM — нормализация нулевого направления может породить некорректный Projectile

Файл: app/src/main/cpp/src/combat/projectile.cpp, spawnProjectile()

Используется:

    glm::normalize(p.direction) * p.speed

без проверки длины направления.

Нулевой или почти нулевой вектор делает normalize() некорректным и может протащить нечисловые значения в скорость, позицию и дальнейшую физику.

Как исправлять: отклонять нулевое направление или задавать безопасный fallback до normalize().

## MEDIUM — ID квестов не гарантированно уникальны после перезапуска

Файлы:
- app/src/main/cpp/src/quests/quest.cpp
- app/src/main/cpp/src/quests/quest_generator.cpp

Счётчик начинается с 1 при каждом процессе:

    std::atomic<u32> gQuestIdCounter{ 1 };

При загрузке сохранённые Quest::id восстанавливаются, но глобальный счётчик не поднимается выше максимального загруженного ID.

После перезапуска новый генерируемый квест может получить ID уже существующего сохранённого квеста.

Поскольку dialogue.cpp сравнивает requireQuestId с q->id, одинаковые ID способны смешать логические задания.

Как исправлять: после загрузки выставлять счётчик выше максимального восстановленного ID или перейти на устойчивые глобальные идентификаторы.

## Рекомендуемые первичные runtime-проверки

1. Изменить блок в удалённом чанке -> сохранить -> полностью выгрузить/перезапустить -> вернуться к нему.
2. Умереть с более чем 20 000 золота.
3. Иметь активный квест NPC -> закрыть игру -> загрузить -> вернуться к этому квестодателю.
4. Иметь два завершённых квеста от разных NPC -> сдать их по отдельности у разных NPC.

Особенно важна первая цепочка: дефект порядка generate -> apply delta затрагивает фундаментальную persistent-state модель мира.
