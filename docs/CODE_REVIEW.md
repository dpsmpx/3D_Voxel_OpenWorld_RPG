## 1. Резюме

Action-RPG: разбиение по подсистемам, именование, границы модулей и покрытие
геймплейных механик соответствуют ТЗ на уровне дизайна. Но как **поставляемый
продукт проект не существует**: он не собирается.

> **Вердикт: ТЗ не выполнено.** Пункт 10 ТЗ («Ожидаемый результат: полный
> исходный код, скрипты сборки, документация, готовый APK») не достигнут ни в
> одной из четырёх частей, кроме документации.

## 3. P0 — блокеры сборки

Пока не устранены все пункты этого раздела, ничего дальше проверить нельзя.

### 3.1. `Entity` объявлена в глобальном пространстве имён, а используется как `ecs::Entity`

*203 ошибки — самая массовая проблема проекта.*

`app/src/main/cpp/src/core/types.h:20` объявляет `struct Entity` **вне**
`namespace ecs`. Весь остальной код (`registry.h` в том числе) обращается к ней
как `ecs::Entity`.

```cpp
// types.h — глобальная область
struct Entity { u32 id = 0; u32 gen = 0; /* ... */ };
```

**Исправление:** перенести `Entity` и специализацию `std::hash<Entity>` внутрь
`namespace ecs` (лучше — в `ecs/registry.h`, `types.h` не должен знать про ECS).

Побочный эффект того же объявления: у `Entity` есть
`operator u32() const`, поэтому в 40+ местах выражения вида `ecs::Entity e = ...`
разбираются как обращение к `glm::e` (константа Эйлера из GLM) и дают каскад
«use of undeclared identifier 'e'».

### 3.7. `-fno-rtti` несовместим с `typeid` в ECS

`CMakeLists.txt:8` и `app/build.gradle` задают `-fno-rtti`, а


(проверено отдельным минимальным примером).

и быстрее, и не требует RTTI:

## 4. P1 — критические дефекты времени исполнения

Эти ошибки не ловятся компилятором и проявятся сразу после устранения P0.

### 4.1. Гонка и use-after-free в `ChunkManager`

`chunk_manager.cpp` раздаёт «сырые» `Chunk*` за пределы блокировки:

* `jobGenerate`/`jobMesh` (строки 80-170) берут `Chunk* c` под `shared_lock`,
  **отпускают блокировку** и работают с указателем всё время выполнения задачи.
* `gatherNeighbors` возвращает указатели на соседей, используемые после
  освобождения `chunksMtx_`.
* `removeChunks` (строка 229) берёт `unique_lock` и **уничтожает** `Chunk` —
  из главного потока, каждые 2 секунды (`main.cpp`, `unloadTimer`).

Результат: воркер продолжает мешить уничтоженный чанк. Кроме того,
`meshesReady_` хранит указатели на потенциально уже удалённые чанки.

`~ChunkManager` ждёт только `meshesInFlight_`, который **не инкрементируется для
задач генерации** — значит, деструктор может завершиться, пока `jobGenerate`
ещё пишет в `voxels`.

**Исправление:** хранить `std::shared_ptr<Chunk>` и передавать в задачи
`shared_ptr`, либо ввести пер-чанковый счётчик ссылок и откладывать удаление.

### 4.2. Гонка данных на самих вокселях

`ChunkManager::setVoxel` пишет `c->set(...)` из главного потока, пока
`buildGreedyMesh` читает `c->voxels` в воркере. `version` атомарна, но данные —
нет. Поле `meshes[i].revision = version` записывается, но **нигде не
сравнивается**, то есть защита от устаревшего меша не работает.

Аналогично `mesh_builder.cpp` читает `chunk.meshes[lod].quads` из потока
рендера без `readyMtx_`, под которым их пишет `jobMesh`.

### 4.3. `JobSystem::parallelFor` — гарантированный вечный дедлок

`core/job_system.cpp:183`:

```cpp
Counter c;
c.add((i32)ranges.size());            // +N
for (usize i = 0; i + 1 < ranges.size(); ++i)
    submit(&c, &runRange, &ranges[i]); // submit() внутри делает c->add(1) → ещё +(N-1)
...
c.wait();
```

Итог: счётчик доходит до `2N-1`, уменьшается на `N` → застревает на `N-1` и
`c.wait()` **никогда не вернётся** при `N > 1`.

**Исправление:** убрать `c.add((i32)ranges.size())` — `submit(Counter*, ...)`
уже считает сам.

### 4.4. `mem::Arena` падает на первом же вызове

`core/memory.h:39`:

```cpp
void* alloc(usize size, usize align) {
    usize aligned = (offset_ + mask) & ~mask;
    if (aligned + size > blockSize_) { newBlock(); ... }
    void* p = (u8*)blocks_.back() + aligned;   // blocks_ пуст при первом вызове!
```

`newBlock()` — единственное место, где `blocks_` заполняется, и вызывается оно
только при переполнении. Первый маленький `alloc` читает `back()` пустого
вектора → UB.

Вдобавок `alloc` всегда пишет в `blocks_.back()`, игнорируя `current_`, поэтому
после `reset()` и `newBlock()` многоблочная арена работает некорректно.

### 4.5. `mem::Pool<T>` — двойное конструирование и висячие указатели

* `alloc()` делает placement-new поверх уже сконструированного элемента
  `std::vector<T> data_` → утечка для нетривиальных `T`.
* `free()` вызывает `~T()`, после чего деструктор вектора вызовет его ещё раз →
  двойное разрушение.
* `grow()` делает `data_.resize()` → **инвалидирует все ранее выданные `T*`**,
  и `free(p)` начинает вычислять мусорный индекс.

При этом `Arena`, `Pool` и `FrameAllocator` **не используются нигде** — `memory.h`
подключён только в `chunk.cpp`, где не применяется.

### 4.6. Потеря точности времени

`main.cpp:875`:

```cpp
const f32 timeSec = std::chrono::duration<f32>(now.time_since_epoch()).count();
```

Секунды от эпохи ≈ 1.75·10⁹ в `float` дают шаг дискретизации ≈ **128 с**.
Всё, что зависит от `timeSec`, ломается:

* `Spawner::isNight(timeSec)` = `fmod(timeSec, 600.f)` — цикл дня/ночи скачет
  и практически «залипает»;
* анимация в шейдерах (`fogParams.w = time`).

**Исправление:** считать время от старта приложения, а не от эпохи.

### 4.7. Плоскость near во frustum culling заведомо неверна

`core/math.h:56` — комментарий честно признаёт проблему:

```cpp
r3 + r2, // near (для Vulkan Z∈[0,1] — не совсем верно, скорректируем)
```

…и корректировка так и не была сделана. При `GLM_FORCE_DEPTH_ZERO_TO_ONE`
ближняя плоскость извлекается как `r2`, а не `r3 + r2`. Чанки будут отсекаться
и попадать в кадр неправильно.

## 5. Производительность против целевых метрик ТЗ

ТЗ п. 2: 60 FPS на Snapdragon 660, ОЗУ ≤ 1.5 ГБ, генерация чанка ≤ 16 мс.
Текущий дизайн не достигнет ни одной из метрик по архитектурным причинам —
не из-за «недооптимизированности», а из-за конкретных решений.

### 5.1. Маска greedy-meshing: ~73 МБ `memset` на один чанк

`world/chunk.cpp:66`:

```cpp
const i32 MAX = 256;                  // фиксированная маска 256×256
maskU.assign(MAX * MAX, 0);           // 128 КБ
maskF.assign(MAX * MAX, 0);           //  64 КБ
for (u8 face = 0; face < 6; ++face)
  for (i32 slice = 0; slice < dimW; slice += step) {
      std::memset(maskU.data(), 0, sizeof(u16) * MAX * MAX);  // 128 КБ
      std::memset(maskF.data(), 0, sizeof(u8)  * MAX * MAX);  //  64 КБ
```

Число слоёв по 6 граням: 32+32+128+128+32+32 = 384 → **384 × 192 КБ ≈ 73 МБ**
обнуления памяти на один вызов. А `jobMesh` вызывает `buildGreedyMesh`
**четыре раза** (по одному на LOD) → ≈ **295 МБ на чанк**. Бюджет в 16 мс
превышен на порядки.

**Исправление:** размер маски = `dimU × dimV` (макс. 128×128 = 16 КБ),
обнуление только используемой области. `maskF` вообще не читается — удалить.

### 5.2. Полная остановка GPU на каждую загрузку буфера

`render/chunk_renderer.cpp:68` вызывает `ctx.submitOneShot(...)`, а
`vk_context.cpp:478` — это:

```
vkAllocateCommandBuffers → vkCreateFence → vkQueueSubmit
→ vkWaitForFences(UINT64_MAX)   ← полный стол главного потока
→ vkDestroyFence → vkFreeCommandBuffers
```

По **2 вызова на LOD × 4 LOD на чанк** ⇒ 8 полных синхронизаций GPU на каждый
загружаемый чанк. При 225 чанках в радиусе видимости — порядка 1800 стопов.
Это прямое противоречие п. 3.2 ТЗ («многопоточная подготовка команд, двойная
буферизация»).

**Исправление:** накапливать копии в один transfer-командный буфер за кадр и
синхронизировать через семафор/fence кадра, без ожидания на CPU.

### 5.3. Все 4 LOD строятся и загружаются на GPU, рисуется один

`jobMesh` строит 4 меша, `uploadChunks` заливает все 4 в VRAM, а `render`
выбирает один. Четырёхкратный расход видеопамяти и пропускной способности.
LOD должны строиться/заливаться по требованию.

### 5.4. Расход ОЗУ на воксели

`Chunk` = `array<u16, 131072>` (256 КБ) + `array<u8, 131072>` (128 КБ)
= **384 КБ на чанк, без сжатия**. При `viewDistance = 7` (≈ 225 чанков) — 86 МБ
только вокселей, плюс 4 меша на чанк в системной и видеопамяти. При максимуме
`viewDistance = 12` (≈ 452 чанка) — 173 МБ вокселей. Уложиться в 1.5 ГБ,
возможно, удастся, но запаса нет. ТЗ п. 3.4 требует «отдельный массив для
метаданных (поворот, состояние)» — его нет (вместо него `light`).

### 5.5. `discard` в основном шейдере террейна

`shaders/voxel.frag` вызывает `discard` для всей геометрии. На тайловых мобильных
GPU (Adreno/Mali) это отключает early-Z для всего прохода и резко увеличивает
overdraw — прямо против цели «заполнение < 2× overdraw» (п. 3.3). Прозрачные
блоки нужно выделить в отдельный pipeline/проход.

### 5.6. Требования п. 3.3, не реализованные вовсе

| Требование ТЗ | Статус |
|---|---|

### 5.7. Растяжение текстур на greedy-квадах

`chunk.cpp` вычисляет `q.uv` (индекс тайла), но `mesh_builder.cpp:74` натягивает
**один** тайл на весь объединённый квад:

```cpp
tileUV[i] = glm::vec2(u0 + CORNER_UV[i].x * (u1 - u0), ...);
```

А `voxel.frag` делает обычный `texture(atlas, vUv)` без повторения. Квад 16×1
блоков покажет одну растянутую текстуру вместо 16 тайлов — классический
визуальный баг greedy meshing. Нужно передавать размер квада в вершину и
делать `fract()` в шейдере.

### 7.1. Gradle-путь не работает

| Проблема | Файл |
|---|---|
| Нет `gradlew`, `gradlew.bat`, `gradle-wrapper.jar` | `gradle/wrapper/` |
| `packagingOptions { jniLibs { ... } }` находится **внутри `defaultConfig`** — в AGP 8 это `ProductFlavor`, у него нет такого метода → падение конфигурации | `app/build.gradle:24` |

| Манифест содержит `package="com.voxelrpg.game"` **и** в gradle задан `namespace` — AGP 8 считает это ошибкой, а не предупреждением | `AndroidManifest.xml:3` |

### 7.2. Ручной путь (`build.sh`) не доведёт до устанавливаемого APK

* Манифест ссылается на `@mipmap/ic_launcher` и `@mipmap/ic_launcher_round`, но
  **каталога `app/src/main/res` в репозитории нет**. `aapt2 link` упадёт на
  ненайденном ресурсе; fallback-ветка в `build.sh` этого не лечит, т.к. ссылка
  идёт из манифеста, а не из `res.zip`.
* `.so` добавляются командой `zip -q -r ../base.apk lib` — **с компрессией**,
  а манифест объявляет `android:extractNativeLibs="false"`. Такой APK система
  откажется загружать. Нужно `zip -0` (STORE) и `zipalign -p 4`.
* `-flto` задан в `CMAKE_CXX_FLAGS_RELEASE` и `CMAKE_EXE_LINKER_FLAGS_RELEASE`,
  но `native-lib` — `SHARED`, к нему применяется `CMAKE_SHARED_LINKER_FLAGS`.
  LTO-объекты не слинкуются.
* README обещает: «Скрипт `build.sh` автоматически подхватит `release.keystore`».
  На деле `build.sh` работает только с `debug.keystore`.

### 7.3. `push_to_github.sh`

* `git config --global credential.helper store` — сохраняет PAT в открытом виде
  в `~/.git-credentials`.
* `git push -u origin main --force` — безусловный force-push в `main`.

Оба решения стоит пересмотреть: `credential.helper cache` вместо `store`,
и обычный `push` вместо `--force`.
